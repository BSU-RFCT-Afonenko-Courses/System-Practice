# Аннотированные образцы объяснения

Три образца редакции от 19 октября применяют [методику](authoring-methodology.md)
к файловому входу, графу Git и SSH. Каждый содержит теорию, связанную
последовательность экранов и сценарий notes. Аннотации обращены к автору
и рецензенту. Число экранов и абзацев не задаёт шаблона остальных тем.
Ниже сохранены дополнительные образцы объектного конвейера и индекса
из прежней редакции; сложное расхождение состояний используется после
первого знакомства со снимком и веткой.

Команды описывают ожидаемое поведение. Выполнение в согласованной среде
и фактическое отображение проверяет Sol. Методическая калибровка проходит
независимую содержательную и стилистическую рецензию до массового авторства.

## Чтение файла

### Фрагмент теории

Файлы. Каталоги. Командная строка. Рабочий каталог. Относительный путь.

Файловый менеджер показывает файлы внутри выбранного каталога.
Путь задаёт положение файла в дереве каталогов. В учебном дереве два
файла с именем `room A.txt` содержат разные строки:

```text
C:\course\lab\
├── input\
│   └── room A.txt          строка north
└── reports\
    └── input\
        └── room A.txt      строка south
```

Терминал предоставляет окно для ввода команды и просмотра результата.
В этом окне работает PowerShell 7 — оболочка, которая разбирает командную
строку и выполняет указанную операцию. Текущий каталог PowerShell —
`C:\course\lab`. Команда `Get-Location` показывает его в поле `Path`.
Для чтения первого файла используется:

```powershell
Get-Content -LiteralPath '.\input\room A.txt'
```

`Get-Content` — имя команды чтения содержимого. Параметр `-LiteralPath`
принимает путь с буквальными именами: символы имени используются без
раскрытия шаблонов. Одинарные кавычки объединяют путь с пробелом в одно
строковое значение; сами кавычки в имя файла не входят. Команда читает
текст файла и выводит строку `north`.

Путь `C:\course\lab\input\room A.txt` полностью задаёт расположение
в этом дереве. Относительный путь `.\input\room A.txt` начинается
в текущем каталоге: `.` обозначает этот каталог, затем выбираются
`input` и файл `room A.txt`.

Команда `Set-Location -LiteralPath '.\reports'` меняет текущий каталог
на `C:\course\lab\reports`. Повтор чтения `.\input\room A.txt` выводит
`south`, поскольку путь теперь проходит через `reports\input`.
Путь `..\input\room A.txt` начинается с перехода к родительскому `lab`
и приводит к первому файлу со строкой `north`.

В Linux такое же учебное дерево размещено в `/home/student/lab`.
В оболочке fish `pwd` показывает текущий каталог, `cd reports` переходит
в `reports`, внешняя программа `cat` читает файл:

```fish
cat './input/room A.txt'
cd reports
cat './input/room A.txt'
cat '../input/room A.txt'
```

При начальном каталоге `/home/student/lab` три чтения дают `north`,
`south`, `north`. Компоненты пути разделяются `/`, кавычки сохраняют
пробел в одном аргументе `cat`. В этом дереве символических ссылок нет.

### Последовательность экранов

#### Файл в каталоге

PowerShell 7 работает в окне терминала. Оболочка выполняет введённую
команду; текущий каталог — `C:\course\lab`.

```text
C:\course\lab\
└── input\
    └── room A.txt → north
```

```powershell
Get-Content -LiteralPath '.\input\room A.txt'
```

Результат — `north`. `Get-Content` читает содержимое файла.
`-LiteralPath` принимает буквальный путь; кавычки сохраняют пробел
в единственном значении пути. `.` выбирает текущий каталог.

**Notes.** Предложить указать тот же файл в дереве файлового менеджера.
Попросить назвать действие, каталог начала пути и имя файла. Ожидаемое
объяснение: чтение начинается в `lab`, затем выбираются `input` и
`room A.txt`. До следующего экрана сообщить переход в `reports` и
предложить определить, что понадобится знать для повторения чтения.

#### Рабочий каталог

В дереве два файла:

```text
C:\course\lab\input\room A.txt          → north
C:\course\lab\reports\input\room A.txt  → south
```

```powershell
Set-Location -LiteralPath '.\reports'
Get-Location
Get-Content -LiteralPath '.\input\room A.txt'
```

`Path` указывает `C:\course\lab\reports`; чтение выводит `south`.
Относительный путь начинается в новом каталоге и выбирает его подкаталог
`input`. Содержимое первого файла сохранилось.

**Notes.** Попросить провести путь по второй строке схемы. При ответе
`north` вернуть внимание к `Path`. Перед следующим экраном предложить
указать путь к первоначальному файлу, начиная из `reports`.

#### Родительский каталог

Текущий каталог — `C:\course\lab\reports`.

```powershell
Get-Content -LiteralPath '..\input\room A.txt'
```

```text
reports → .. → lab → input → room A.txt → north
```

`..` выбирает родительский каталог. Последующие компоненты приводят
к `C:\course\lab\input\room A.txt`; результат чтения — `north`.

**Notes.** Сопоставить ответ с прогнозом. Попросить записать полный путь
и объяснить сохранение результата при другом текущем каталоге, если
чтение получает этот полный путь. Затем показать соответствующий
Linux-путь на том же дереве и назвать разделитель компонентов.

### Авторские решения

Начало использует знакомую файловую операцию. До первой команды введены
терминал, оболочка и местоположение файла. Одно дерево и два содержимых
дают наблюдаемую причину изменения результата. Notes направляют действие
с видимой схемой; существенные определения остаются на экранах.

Основание: Jones, печ. 1–4/PDF 26–29; TLCL, печ. 7–12/PDF 31–36;
[Get-Content](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-content?view=powershell-7.5),
[Set-Location](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/set-location?view=powershell-7.5),
[fish Running Commands](https://fishshell.com/docs/current/tutorial.html#running-commands).
Дерево и данные созданы для курса. Полный fish-маршрут размещается
в теории и практической подготовке; основная экранная последовательность
сохраняет PowerShell/Windows.

## Ветка Git

### Фрагмент теории

Снимок проекта. Коммит. Родитель. Ветка. HEAD. Подготовка изменения.

Репозиторий Git хранит версии файлов и историю их связи. Коммит ссылается
на снимок проекта и содержит сведения об авторе, сообщение и родителей.
Обычный коммит продолжает предыдущий одним родителем. У начального
коммита родителей нет.

В небольшом проекте отслеживается `settings.txt` со строкой `limit=10`.
Начальный коммит обозначен A. Это условное имя в схеме; в репозитории
коммит имеет идентификатор. Ветка `main` указывает на A. Ветка — именованная
изменяемая ссылка на коммит. HEAD в этом состоянии указывает на активную
ветку `main`. Рабочее дерево содержит редактируемые файлы; индекс хранит
подготовленное содержимое следующего снимка. Оба сейчас совпадают с A.

```text
A
↑
main ← HEAD

Снимок A: settings.txt содержит limit=10
```

`git branch tune` создаёт ссылку `tune` на A. `git switch tune` делает
`tune` активной. Обе ветки пока обозначают тот же снимок, поэтому
содержимое файла сохраняется. После изменения строки на `limit=12`
в редакторе команда `git add settings.txt` подготавливает её в индексе.
Обычная команда `git commit -m "Уточнить предел"` создаёт коммит B:

```text
A ← B ← tune ← HEAD
↑
main

Снимок A: limit=10; снимок B: limit=12
```

Связь A ← B указывает родителя B. B хранит подготовленное содержимое,
`tune` перемещается на B, `main` продолжает указывать на A.
Рабочий файл и индекс после этого опыта содержат `limit=12`.

При чистом рабочем дереве `git switch main` переключает HEAD на `main`
и восстанавливает отслеживаемый файл со строкой `limit=10`. Ветка `tune`
сохраняет B; его снимок доступен для дальнейшей работы.

### Последовательность экранов

#### Снимок проекта

Начальный коммит A содержит `settings.txt` со строкой `limit=10`.
Рабочее дерево содержит редактируемые файлы проекта; индекс хранит
подготовленное содержимое следующего снимка. Содержимое `settings.txt`
в рабочем дереве и индексе сейчас совпадает со снимком A.

```text
A
↑
main ← HEAD

Снимок A: settings.txt содержит limit=10
```

Коммит хранит ссылку на снимок и сведения об изменении. Ветка `main`
указывает на коммит. HEAD указывает на активную ветку. A — обозначение
коммита на схеме; родителей у этого начального коммита нет.

**Notes.** Попросить найти файл в снимке и активную ветку. До следующего
экрана предложить предсказать действие `git branch tune`: какие существующие
объекты нужны новой ветке, если её работа начинается с A.

#### Создание ветки

```text
git branch tune
```

```text
A ← tune
↑
main ← HEAD

Снимок A: settings.txt содержит limit=10
```

Создана ссылка `tune` на A. HEAD сохраняет `main` активной.
Файл, индекс и история коммитов сохранили исходное состояние.

**Notes.** Сопоставить граф с прогнозом. Попросить назвать число коммитов
и число веток. Ожидаемый ответ: один коммит и две ветки. Перед продолжением
предложить указать, какую связь должно изменить переключение на `tune`.

#### Подготовка снимка

После `git switch tune` HEAD указывает на `tune`. В редакторе строка
`settings.txt` изменена на `limit=12`, затем выполнено:

```text
git add settings.txt
```

```text
A ← tune ← HEAD
↑
main
```

| Снимок A | Индекс | Рабочий файл |
|---|---|---|
| `limit=10` | `limit=12` | `limit=12` |

Индекс содержит подготовленный вариант. Коммит A сохраняет прежний снимок.

**Notes.** Попросить выбрать ячейку с содержимым будущего обычного коммита.
Перед раскрытием следующего графа предложить предсказать родителя нового
коммита и ссылку, которая переместится.

#### Новый коммит

```text
git commit -m "Уточнить предел"
```

```text
A ← B ← tune ← HEAD
↑
main

Снимок A: limit=10; снимок B: limit=12
```

B хранит `limit=12` и ссылается на родителя A. Ветка `tune` переместилась
на B. `main` указывает на A. Индекс и рабочий файл совпадают со снимком B.

**Notes.** Сопоставить две изменившиеся части: новый узел B и положение
`tune`. Попросить объяснить сохранность A. До следующего экрана предложить
предсказать содержимое файла после переключения на `main`.

#### Переключение

Незавершённых изменений нет.

```text
git switch main
```

```text
A ← B ← tune
↑
main ← HEAD

Снимок A: limit=10; снимок B: limit=12
```

Рабочий `settings.txt` и индекс содержат `limit=10`, как снимок A.
`tune` сохраняет B с `limit=12`. Связь A ← B по-прежнему обозначает
родителя; переключение сохранило историю коммитов.

**Notes.** Попросить указать ветку, в которой доступно значение 12,
и команду переключения к ней. Ожидаемый ответ — `tune`, `git switch tune`.
Сопоставить восстановленное содержимое рабочего файла с неизменным графом.

### Авторские решения

Сначала показан один понятный снимок. Создание ссылки, выбор активной ветки,
подготовка содержимого и новый коммит разведены по действиям. Схема всегда
обозначает отношение к родителю в одном направлении. Таблица дополняет
граф конкретным содержимым файла. Чистое состояние при переключении
сохраняет простоту первого опыта; случаи незавершённых правок получают
отдельное объяснение.

Основание: Pro Git, печ. 14–18 и 66–71/PDF 20–24 и 72–77;
[git-commit](https://git-scm.com/docs/git-commit) и
[git-switch](https://git-scm.com/docs/git-switch). Имена, данные и схема
созданы для курса. Sol создаёт начальный репозиторий с локальной учебной
identity, веткой `main` и одним отслеживаемым файлом. Пользовательская
глобальная конфигурация для этого опыта не меняется.

## Проверка SSH-соединения

### Фрагмент теории

Ключ сервера. Защищённый канал. Аутентификация пользователя. Права доступа.

SSH позволяет передавать команды и данные через защищённое соединение.
При обращении Git к GitHub по SSH клиент сначала устанавливает транспорт
с сервером. В ходе обмена ключами сервер подтверждает владение своим
закрытым ключом. Клиент проверяет подпись и принадлежность открытого ключа
серверу. При первом подключении пользователь сверяет показанный отпечаток
с текущими [отпечатками GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints).
После совпадения отпечатков пользователь подтверждает ключ в запросе
OpenSSH. Клиент сохраняет принятую запись в `known_hosts`.
Несовпадение требует выяснить причину до продолжения.

Согласованные сеансовые ключи защищают конфиденциальность и целостность
дальнейшего обмена. Внутри этого транспорта клиент подтверждает аккаунт:
создаёт подпись данных текущего сеанса закрытым пользовательским ключом.
GitHub проверяет её открытым ключом, ранее добавленным в аккаунт.
Закрытый ключ остаётся на компьютере клиента. Парольная фраза защищает
его сохранённый файл; агент может выполнять подпись загруженным ключом.
Модель транспорта описана в [RFC 4253](https://www.rfc-editor.org/rfc/rfc4253),
пользовательской подписи — в [RFC 4252, §7](https://www.rfc-editor.org/rfc/rfc4252#section-7).

Для опыта уже подготовлен аккаунт GitHub, открытый ключ добавлен в него,
а выбранный SSH-клиент имеет доступ к соответствующему закрытому ключу.
В PowerShell 7 выполняется:

```powershell
ssh -T git@github.com
$LASTEXITCODE
```

`ssh` запускает клиент, `-T` отключает выделение псевдотерминала.
`git` в адресе — служебное имя пользователя SSH на GitHub; аккаунт определяется
предъявленным ключом. При успехе сообщение называет распознанный аккаунт
и сообщает об отсутствии интерактивной оболочки. Ожидаемый код — `1`;
`$LASTEXITCODE` показывает код только что завершённой внешней программы.
Это поведение установлено [инструкцией GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/testing-your-ssh-connection).

Тест подтверждает аутентификацию аккаунта. При Git-операции с адресом
`git@github.com:owner/repo.git` сервер дополнительно проверяет право
этого аккаунта читать или изменять репозиторий `owner/repo`.
Здесь `owner` и `repo` заменяются владельцем и именем учебного репозитория.

### Последовательность экранов

#### Проверка сервера

```text
Клиент OpenSSH                    GitHub
       ─── установление соединения ───→
       ←── ключ сервера и подпись ─────
       проверка подписи и отпечатка
       ═══ защищённый транспорт ══════
```

Ключ сервера участвует в подтверждении стороны соединения.
При первом доступе отпечаток сверяется с официальным списком GitHub.
Подтверждённая запись сохраняется для последующих соединений.
Сеансовые ключи защищают дальнейшие данные от чтения и незаметного
изменения при передаче.

**Notes.** Указать на клиент как сторону, принимающую решение о доверии
серверу. Предложить назвать источник отпечатка. Ожидаемый ответ — текущая
официальная страница GitHub. Разобрать несовпадение: остановить соединение
и проверить адрес и официальные сведения.

#### Подтверждение аккаунта

Открытый пользовательский ключ уже добавлен в аккаунт GitHub.
Защищённый транспорт установлен.

```text
Клиент: закрытый ключ             GitHub: открытый ключ аккаунта
       ─── подпись данных сеанса ───→ проверка подписи
       ←── распознанный аккаунт ─────
```

Клиент создаёт подпись своим закрытым ключом. GitHub проверяет подпись
по зарегистрированному открытому ключу. Закрытый ключ остаётся у клиента.
Агент позволяет клиенту запросить подпись загруженным ключом.

**Notes.** Попросить назвать, какой ключ студент добавлял в аккаунт.
Ожидаемый ответ — открытый. Указать место создания подписи и место
её проверки. Перед тестом предложить определить, какую информацию
об аккаунте должно содержать успешное сообщение.

#### Результат проверки

Подготовлены аккаунт, зарегистрированный открытый ключ и выбранный
SSH-клиент с доступом к закрытому ключу. В PowerShell 7:

```powershell
ssh -T git@github.com
$LASTEXITCODE
```

При успехе сообщение GitHub содержит имя распознанного аккаунта,
подтверждение аутентификации и указание, что интерактивная оболочка
не предоставляется. Ожидаемый код теста — `1`.

`-T` отключает выделение псевдотерминала. `git` — служебное имя SSH;
GitHub определяет аккаунт по ключу. `$LASTEXITCODE` показывает код
завершения `ssh`.

**Notes.** Сопоставить аккаунт с ожидаемым. Разобрать успешное сообщение
и отказ `Permission denied (publickey)`: во втором случае проверить
выбор клиента, доступ к ключу и регистрацию открытого ключа.
До следующего экрана предложить определить, достаточно ли названного
аккаунта для записи в любой репозиторий.

#### Доступ к репозиторию

```text
git@github.com:owner/repo.git
```

`owner/repo` задаёт конкретный репозиторий. При чтении или записи
GitHub проверяет права распознанного аккаунта на эту операцию.
Публикация изменений через push и получение истории во второй копии
показывают результат реального обмена.

Видимость репозитория определяет доступ к файлам на GitHub.
Защищённый канал действует во время передачи.

**Notes.** Предложить объяснить случай: тест SSH называет правильный
аккаунт, push получает отказ в доступе. Ожидаемое направление — адрес
репозитория и права на запись. Попросить назвать два наблюдения после
успешного обмена: нужный коммит в другой копии и соответствующее содержимое.

### Авторские решения

Образец калибрует один шаг уже подготовленного доступа. Условия подготовки
видны перед командой. Схема разделяет проверку сервера, канал и пользовательскую
подпись; сообщение теста связано с проверяемым результатом. Полная инструкция
лабораторной дополнительно раскрывает регистрацию, проверку существующих
ключей, создание пары и согласование OpenSSH/агента на Windows по
[текущей инструкции GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

Криптографические схемы показывают отношения без переноса устаревших наборов
алгоритмов RFC в настройку. Отпечаток не закреплён как вечная константа.
Полноценный Windows-маршрут и внешнее соединение требуют собственного
испытания Sol. Учебный фрагмент не является свидетельством выполненного
внешнего опыта.

## Объекты в конвейере

### Фрагмент теории

Объект объединяет именованные свойства. В наборе измерений каждый
объект имеет `Sensor` с именем датчика
и целочисленное `Value` со значением измерения:

```powershell
$readings = @(
    [pscustomobject]@{ Sensor = 'A'; Value = 12 }
    [pscustomobject]@{ Sensor = 'B'; Value = 3 }
    [pscustomobject]@{ Sensor = 'C'; Value = 20 }
)
```

`[pscustomobject]` создаёт объект из записанных имён и значений.
`@(...)` собирает три объекта в массив. Цель обработки — сохранить
измерения со значением не меньше 10, расположив большие значения первыми.

Оператор `|` передаёт вывод слева следующей команде, принимающей ввод
из конвейера. При передаче `$readings` в конвейер по одному поступают
три объекта из массива. Для каждого из них `Where-Object` вычисляет
условие в `{ ... }`; переменная `$_` обозначает текущий объект.

```powershell
$readings |
    Where-Object { $_.Value -ge 10 } |
    Sort-Object -Property Value -Descending |
    Select-Object -Property Sensor,Value |
    Export-Csv -Path './report.csv' -NoTypeInformation -Encoding utf8
```

В условии `Where-Object` оператор `-ge` проверяет отношение
«больше или равно». Фильтр пропускает объекты A и C. `Sort-Object`
сначала получает все прошедшие отбор объекты, затем выдаёт их
по убыванию числового `Value`: C перед A.
`Select-Object` создаёт выходные объекты с выбранными свойствами.
`Export-Csv` записывает значения этих свойств в CSV-файл:

```csv
"Sensor","Value"
"C","20"
"A","12"
```

При обычном выводе в терминал PowerShell формирует экранное представление
объектов. `Format-Table` создаёт инструкции табличного форматирования.
Если подать их в `Export-Csv`, файл будет описывать объекты форматирования.
Для указанного отчёта экспорт получает объекты с `Sensor` и `Value`.

### Последовательность экранов

#### Свойства измерения

Каждая запись имеет имя датчика `Sensor` и целочисленное значение `Value`:

```powershell
$readings = @(
    [pscustomobject]@{ Sensor = 'A'; Value = 12 }
    [pscustomobject]@{ Sensor = 'B'; Value = 3 }
    [pscustomobject]@{ Sensor = 'C'; Value = 20 }
)
```

`[pscustomobject]` создаёт отдельный объект, `@(...)` собирает их в массив.
Обращение к свойству использует его имя. Экранная таблица является
представлением этих данных.

**Notes.** Попросить назвать тип значения `Value` и установить,
какие два объекта удовлетворят границе 10. До следующего экрана
предложить упорядочить их по убыванию числового значения.

#### Отбор и сортировка

`|` передаёт вывод следующей команде, принимающей ввод из конвейера.
Из массива `$readings` по одному поступают три объекта. Для каждого
`Where-Object` вычисляет условие: `$_` обозначает текущий объект,
`-ge` проверяет отношение «больше или равно».

```powershell
$readings |
    Where-Object { $_.Value -ge 10 } |
    Sort-Object -Property Value -Descending
```

```text
A:12, B:3, C:20 → отбор Value ≥ 10 → A:12, C:20
               → сортировка по убыванию Value → C:20, A:12
```

Фильтр пропускает A и C. `Sort-Object` получает все прошедшие отбор
объекты, затем выдаёт их по убыванию `Value`.

**Notes.** Сопоставить результат с прогнозом. Попросить указать стадию,
после которой B перестал участвовать. Разобрать, почему для окончательного
порядка сортировке нужны все входные объекты. Обсудить, какое изменение понадобится,
если значения поступят из текстового файла строками: преобразование
к числу должно получить явное место до числового сравнения и сортировки.

#### Сериализация результата

После отбора и сортировки получены C:20 и A:12. Продолжение конвейера:

```powershell
Select-Object -Property Sensor,Value |
    Export-Csv -Path './report.csv' -NoTypeInformation -Encoding utf8
```

`Select-Object` задаёт свойства выходных объектов. `Export-Csv`
сохраняет их в файле с полями `Sensor,Value`:

```csv
"Sensor","Value"
"C","20"
"A","12"
```

`Format-Table` создаёт объекты экранного форматирования. Для этого отчёта
перед экспортом сохраняются объекты измерений с выбранными свойствами.

**Notes.** Соединить показанное продолжение с конвейером прошлого экрана
перед запуском. Предложить назвать данные на входе экспорта. Сопоставить
имена свойств с заголовком CSV. Разобрать предполагаемую вставку
`Format-Table`: какой тип данных тогда получит следующая команда.

### Авторские решения

Данные малы и полностью видны. Отбор, сортировка, выбор свойств
и сериализация получают отдельные функции. Перед первым конвейером
и на видимом экране объяснены соединение команд, принимающих конвейерный
ввод, перечисление элементов массива и условие для текущего объекта.
Сортировка получает весь вход до выдачи окончательного порядка.
Общее объяснение объектов поддерживается конкретными состояниями.
Учебный фрагмент-продолжение
подписан как часть конвейера; запускать его отдельно от входа не предлагается.

Основание: Jones, гл. 6, печ. 61–71/PDF 86–96; Петти и др.,
гл. 12, печ./PDF 141–147. Поэлементная модель уточнена по
[about_Pipelines](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pipelines?view=powershell-7.5).
Граница форматирования подтверждена примером 7
[Export-Csv](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/export-csv?view=powershell-7.5).
Объекты и значения созданы автором; вывод обозначает ожидаемый результат.

## Содержимое коммита

### Фрагмент теории

Индекс Git содержит подготовленное состояние следующего коммита.
Рабочее дерево содержит редактируемые файлы. `HEAD` в данном опыте
обозначает текущий коммит через активную ветку. Добавление файла
в индекс сохраняет его содержимое на момент операции.

В начальном коммите учебного репозитория файл `settings.txt` содержит
одну строку `limit=10`. Рабочее дерево и индекс совпадают с этим коммитом.
Редактор заменил строку на `limit=12`; после этого выполнено:

```text
git add settings.txt
```

Затем в редакторе значение изменили ещё раз, на `limit=20`, без повторного
добавления в индекс. Получилось три состояния одного пути:

| Место | Содержимое `settings.txt` |
|---|---|
| Текущий коммит HEAD | `limit=10` |
| Индекс | `limit=12` |
| Рабочее дерево | `limit=20` |

`git diff -- settings.txt` сравнивает рабочее дерево с индексом
и показывает изменение 12 → 20. `git diff --staged -- settings.txt`
сравнивает индекс с HEAD и показывает изменение 10 → 12.
Обычный `git commit` сохранит подготовленную строку `limit=12`.
Рабочий файл сохранит `limit=20`; оставшаяся правка доступна для
отдельного решения о следующем коммите.

### Последовательность экранов

#### Подготовленное состояние

Начальный коммит и оба текущих состояния `settings.txt` содержат `limit=10`.
После замены в редакторе на `limit=12` и `git add settings.txt`:

| HEAD | Индекс | Рабочий файл |
|---|---|---|
| `limit=10` | `limit=12` | `limit=12` |

`git add` записал в индекс содержимое файла на момент команды.
Индекс определяет подготовленный снимок следующего коммита.

**Notes.** Попросить назвать состояние, которое сохранит обычный коммит.
До следующего экрана сообщить действие редактора: заменить 12 на 20
без нового `git add`. Предложить предсказать все три ячейки таблицы.

#### Независимая рабочая правка

После повторного редактирования:

| HEAD | Индекс | Рабочий файл |
|---|---|---|
| `limit=10` | `limit=12` | `limit=20` |

| Команда | Сравниваемые состояния | Видимое изменение |
|---|---|---|
| `git diff -- settings.txt` | Индекс → рабочее дерево | 12 → 20 |
| `git diff --staged -- settings.txt` | HEAD → индекс | 10 → 12 |

Редактор изменил рабочий файл. Подготовленная версия в индексе сохранила 12.

**Notes.** Сопоставить таблицу с прогнозом. Попросить выбрать сравнение
для проверки содержания будущего коммита. До раскрытия следующего экрана
предложить предсказать значение в рабочем файле после обычного коммита.

#### Сохранение снимка

```text
git commit -m "Уточнить предел измерения"
```

| Новый HEAD | Индекс | Рабочий файл |
|---|---|---|
| `limit=12` | `limit=12` | `limit=20` |

Коммит сохранил подготовленное состояние. Значение 20 осталось рабочей
правкой относительно него. Сравнение `git diff -- settings.txt`
по-прежнему показывает 12 → 20.

**Notes.** Попросить объяснить, какие данные нужно предъявить для проверки
обоих результатов: содержимое коммита и содержимое рабочего файла.
Предложить назвать действие, которым студент сознательно подготовит
оставшуюся правку к следующему коммиту.

### Авторские решения

Таблица сохраняет один путь и показывает три конкретных содержания.
Команды сравнения получают явные стороны. Отдельные значения предотвращают
неопределённый рассказ о «сохранении файла». Последний экран даёт полезное
следствие: подготовленная правка зафиксирована, незавершённая остаётся
доступной. Сценарий notes ставит прогноз перед результатом.

Основание: Pro Git, печ. 17–18 и 29–39/PDF 23–24 и 35–45;
точные формы сравнений — [git-diff](https://git-scm.com/docs/git-diff).
Это собственный числовой опыт на основе модели индекса; книжные файлы,
сюжет и изображения не воспроизводятся. При проверке Sol создаёт исходный
коммит, локальную учебную identity и чистое начальное состояние.

## Калибровка самостоятельной задачи

Демонстрация индекса показывает определённую последовательность действий.
Самостоятельное условие получает новые данные и цель, например:
«В проекте имеются две независимые правки. Сохраните исправление описания
формата отдельным коммитом. Незавершённое изменение образца данных
оставьте в рабочем дереве; индекс после сдачи должен совпадать с HEAD».
Полный контракт дополнит точные файлы, содержимое и способ сдачи истории.
Команды выполнения в это условие не переносятся.

Отрицательный методический вариант: после приведённого условия перечислить
`git add`, `git commit` и необходимые аргументы по шагам. Такой список
выполняет работу выбора, предназначенную студенту. Во введении похожая
последовательность уместна при восстановлении знакомого решения.

Отрицательный редакторский вариант: «Эти команды отвечают за разные
стороны работы с репозиторием». После таблицы конкретных сравнений
он не добавляет отношения или следствия. Его удаляют без декоративной
замены. Предметные условия, например существование начального HEAD
и отсутствие повторного добавления в индекс, сохраняются.
