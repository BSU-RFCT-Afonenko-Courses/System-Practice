# Локальная техническая сборка

Инструменты сборки предназначены для автора и преподавателя. Они не добавляют
Python, Quarto или JDK к требованиям студенческих заданий на сценарии и Git.
На проверенном CachyOS Task 3.54 запускается командой `go-task`.

Получите исходные зависимости штатным Git: `git submodule update --init`
либо `go-task bootstrap`. Для обычной student-сборки с уже установленными расширениями:

```sh
go-task test:materials
go-task render
```

`render:full` отдельно выбирает профиль `full`. Установка расширений описана
в [инструкции](provider-installation.md); render не устанавливает зависимости
и не проверяет vendor inventory.

После авторского изменения объявленных исходных данных выполните
`go-task materials:write`. Команда создаёт ZIP трёх лабораторных,
добровольного проекта и публичные копии демонстрационных наборов.
Самостоятельные Quarto-проекты теории и справочника получают копии из
`practice/materials`. Упаковщики проверяют безопасные пути перед записью
и заменяют объявленные назначения. Сохраните нужные локальные изменения
обычными средствами Git. Hash manifests, `materials:check` и запрет ручной
правки generated-файлов удалены; render/preview не зависят от такой проверки.
Учебный договор перед изменением данных требует авторского согласования.

После изменения рецептов, исходных данных или `student/README.md` двух
готовых Git-входов сначала регенерируйте материалы из корня репозитория:

```sh
python3 tools/build_git_materials.py
```

Уже указанная `go-task materials:write` включает эту подготовку. Инструмент
вызывает существующие `generate(destination, empty_template)` из
`tasks/projects/version-control/github-ssh/seed_recipe.py` и
`tasks/projects/version-control/restore-selected-state/seed_recipe.py`;
оба материала подготавливаются до записи публичных назначений. Эти два
вызова включают суммарно 27 дочерних команд Git. Предыдущие ZIP и результаты
render/native export для регенерации не нужны. Сохраните обновлённые материалы
перед сборкой; обычные render/preview копируют готовые ресурсы и Git не запускают.

Результаты — `tasks/materials/version-control-github-ssh-start.zip` и
`tasks/materials/version-control-restore-selected-state-start.zip`. Это
самостоятельные предоставленные ZIP с точным исходным README и обычным
репозиторием под `versioning/project/` либо `work/`, включая `.git`. Полный
native PL `starter.zip` формируется отдельно. Полные условия сохраняются
в книге, conditions ZIP/README и PL condition/README.

На каждом профиле `student`/`full` выдаются 5 contextual model ZIP,
7 conditions model ZIP и 2 предоставленных Git ZIP: всего 7 стартовых входов
и 7 полных условий. Общий состав исходных материалов увеличивается с 14 до
16 ZIP. Прежние две неверные contextual выдачи каждого профиля удаляются
штатной очисткой Download; новую выдачу проверяют по фактическим файлам и ссылкам.

`test:materials` запускает существующий unittest suite: содержимое ZIP,
реальные Git index/trees/history, допустимые решения, отрицательные случаи
и готовые fish/PowerShell scripts по файлам, stdout и exit codes. Проверки
безопасных путей и отсутствия частной конфигурации сохранены. Повторяемость
bytes/mtime и отказ на любую ручную правку больше не являются критериями.

Для строгой проверки собственных Python-инструментов установите закреплённый
checker из корня репозитория и выполните:

```sh
python3 -m pip install -r requirements-typecheck.txt
python3 -m pyright --project pyrightconfig.json
```

`requirements-typecheck.txt` закрепляет pyright 1.1.414; область собственных
файлов задаёт `pyrightconfig.json` в режиме strict, включая новые файлы. Установленные расширения
и vendor-код не включаются в эту собственную область.

TypeScript и точный встроенный JavaScript проверяются штатным Quarto:

```sh
quarto run tests/typecheck.ts
```

Драйвер использует настоящие Quarto stdlib/path/fs aliases, рекурсивно обнаруживает и проверяет собственные
TS-файлы и отдельно единственный script из `includes/reveal-layout.html`
со strict/checkJs и DOM. Для всего графа импортов нужны согласованные версии
установленных расширений; отдельный `deno check` без штатной карты импортов
не заменяет эту команду. CSS из `includes/book-tables.html` отдельно проверяется Stylelint
после извлечения единственного style-фрагмента.

Существующие Python-тесты запускаются так:

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Проверка типов, синтаксиса,
упаковки и исполнения сценариев имеет отдельные результаты; одна успешная
стадия не подтверждает остальные.

`tools/check_data_processing.py` читает опубликованные файлы и результаты,
не исполняя присланный код. Его `automated: pass` и код CLI 0 означают совпадение
проверяемых файлов; установленное нарушение даёт `fail` и код 1. Ограничение
архивного инструмента даёт `manual`, `toolLimited: true`, `diagnostics`, пустой
`errors` и код 2: это основание для ручной проверки. ZIP/tar.gz guards
безопасных путей и состава архивов остаются в `tools/system_support.py`
и проверяются отдельными тестами.

Файловая проверка сохраняет `manualRequired`: смысл конвейеров,
самостоятельность, реальные запуски, команды и объяснения по одним итоговым
файлам не устанавливаются. Самостоятельные задания на рабочую среду и Git
проверяются по своим условиям и ручным критериям. PowerShell/Git проверяются
отдельно от fish grader.
Локальный запуск на Linux не подтверждает Windows, облачную рабочую область
или реальный Moodle. Успех CI не подтверждает готовность всего выпуска.

`publish` изменяет внешний сайт и выполняется только разрешённым действием
после предъявления конкретного результата. Нового receipt/source-hash
требования для обычной сборки нет.


`go-task check` последовательно выполняет `check:code`, `check:quarto`
и `check-format`. Последняя команда проверяет форматирование без записи;
`go-task format` применяет его. Собственные новые файлы обнаруживаются
рекурсивно. Зависимости `.platform`, `.ci`, `_extensions`, vendor,
генерируемые outputs и исторические `docs/superpowers` исключены.

Роли инструментов разделены по форматам: Ruff форматирует Python и проверяет
E4/E7/E9/F/B; shfmt форматирует Bash, fish_indent — fish, PSScriptAnalyzer
Invoke-Formatter — PowerShell, Prettier — JSON/YAML/CSS/HTML/TypeScript,
Panache — QMD. Prettier не форматирует код внутри HTML; встроенный JavaScript
по-прежнему проходит строгую проверку Quarto. ShellCheck и штатные парсеры
Bash/fish дополняют форматирование. Actionlint проверяет workflows, yamllint —
синтаксис YAML и повторные ключи, jq — синтаксис JSON, Taplo без сетевых схем — синтаксис TOML,
xmllint без сети — XML/CSL. Stylelint проверяет CSS-свойства и структуру,
HTML Validate — include-фрагменты; проверка итогового DOM остаётся стадией render.

Panache выполняет полный структурный проход из 26 правил. Namespace-ссылки
и библиографию продолжает проверять QRC при штатной сборке. Форматирование
QMD сохраняет переносы прозы и содержимое кодовых блоков; внешние форматтеры
не подключены. Это техническая обработка Markdown, условия и оценивание
сохраняются.

Для PowerShell нужны PowerShell 7 и установленный штатным `Install-Module`
модуль PSScriptAnalyzer. `tools/check-powershell.ps1` отдельно вызывает
`Parser.ParseFile` и затем анализатор без фильтра Severity: синтаксическая
ошибка не теряется среди предупреждений. Единственное контекстное исключение
`PSUseBOMForUnicodeEncodedFile` задано в `PSScriptAnalyzerSettings.psd1`:
PowerShell 7 на Windows читает UTF-8 без BOM, и этот формат уже является
договором учебных файлов. Windows PowerShell 5 не входит в целевую среду.

CI устанавливает эти авторские инструменты стандартными package-командами
и вызывает те же Task targets. Локально требуются команды из PATH; проверки
ничего не устанавливают. Отсутствующий инструмент или его отказ дают
ненулевой результат. Запуск на Linux не подтверждает выполнение на Windows.
