4  Управление версиями

Темы раздела: начальная настройка; состояние файлов; снимок; история; ветки; слияние; удалённые репозитории; SSH; упаковка результата. Команды Git выполняются в корне нужного репозитория; переход в другой каталог указан отдельно. Механизмы разобраны в теории состояния репозитория, ветвления и обмена.

4.1 Начальная настройка

git --version
git init -b main
git config user.name "Ваше имя"
git config user.email "YOUR_EMAIL"
git config --get user.name
git config --get user.email

init выполняется в выбранной папке исходных файлов. Имя и почту заменяют собственными значениями. Без --global настройка относится к текущему репозиторию. Почта коммитов доступна читателям истории; можно выбрать свой GitHub noreply из настроек аккаунта. Аутентификация аккаунта выполняется при соединении с сервером.

4.2 Наблюдение состояния

Команда Что показывает
git status Текущую ветку, подготовленные/рабочие изменения, состояние слияния
git status --short Краткие состояния путей; для обычного изменённого файла первая колонка относится к индексу, вторая — к рабочему дереву
git --no-pager diff Изменения рабочего дерева относительно индекса
git --no-pager diff --staged Подготовленные изменения относительно HEAD
git --no-pager diff HEAD Рабочее содержимое относительно HEAD
git --no-pager diff ID_A ID_B Различия двух сохранённых снимков

Вместо ID_A/ID_B подставляют идентификаторы из своей истории. --no-pager выводит результат прямо в терминал; -- criteria.txt в конце команды ограничивает наблюдение одним файлом.

Для обычного отслеживаемого файла M означает изменение, пробел — совпадение. MM criteria.txt возможно при пороге 10 в HEAD, 12 в индексе и 20 в рабочем файле. ?? обозначает неотслеживаемый путь; UU — конфликт, в котором обе стороны меняли файл. status, diff.

4.3 Сохранение снимка

git add -- criteria.txt README.md
git --no-pager diff --staged
git commit -m "Описать сохранённое изменение"

add подготавливает содержимое названных файлов в момент вызова. Обычный commit без путей сохраняет подготовленный снимок. После дальнейшей правки рабочего файла индекс сохраняет ранее выбранное содержимое до следующего действия с индексом. Режим commit -a подготавливает изменения и удаления отслеживаемых файлов; новые неотслеживаемые файлы требуют добавления. Руководство commit.

4.4 Чтение истории

git --no-pager log --oneline --decorate
git --no-pager log --graph --oneline --decorate --all
git --no-pager log -p -- criteria.txt
git show 'HEAD:criteria.txt'
git show ':criteria.txt'
git show 'ID_A:criteria.txt'
git --no-pager show --no-patch --format=raw HEAD
git rev-parse HEAD

log начинает обход от HEAD; --all включает все ссылки, --graph рисует родительские связи, --decorate подписывает текущие имена. -p добавляет изменения. Три формы show читают файл из HEAD, индекса и указанного коммита. В raw-описании коммита строки parent называют непосредственных родителей. rev-parse HEAD печатает полный идентификатор. [1, сс. 42–48], [4], [5]

4.5 Восстановление содержимого

Перед заменой рабочего файла прочитайте diff и сохраните полезные правки.

Источник → назначение Команда
Индекс → рабочий файл git restore -- criteria.txt
HEAD → индекс git restore --staged -- criteria.txt
Указанный коммит → рабочий файл git restore --source=ID_A --worktree -- criteria.txt
Указанный коммит → индекс и рабочий файл git restore --source=ID_A --staged --worktree -- criteria.txt

У обычного restore источник по умолчанию — индекс; с --staged — HEAD. Восстановление из старого коммита переносит его содержимое в указанное место. Чтобы закрепить его в новом состоянии истории, подготовьте результат и создайте коммит. Руководство restore.

4.6 Ветки

Действие Команда Наблюдение
Перечислить локальные ветки git branch --list Звёздочкой отмечена текущая
Создать ссылку на текущий коммит git branch seconds Текущая ветка сохраняется
Выбрать существующую ветку git switch seconds HEAD выбирает seconds; при чистом состоянии файлы и индекс обновляются по её снимку
Создать и выбрать ветку git switch -c seconds Новая ветка начинается от текущего коммита
Создать от выбранного коммита git switch -c seconds ID_A Исходный снимок выбирается явно

При переключении Git сохраняет совместимые незавершённые изменения; действие, которое затёрло бы их, блокируется. Status перед переключением помогает установить исходное состояние.

4.7 Слияние

При чистом состоянии текущей main:

git merge --ff-only source-note
Отношение историй Результат ff-only
main — предок source-note main перемещается к её вершине, нового коммита нет
source-note уже включена в историю main Already up to date, продвижение не требуется
Вершины расходятся Отказ; ссылки сохраняются

Для соединения расходящихся main и seconds:

git merge seconds
git status

При конфликте прочитайте обе версии и их смысл, приведите файл к согласованному состоянию, удалите маркеры, проверьте результат:

git add -- criteria.txt
git --no-pager diff --staged
git commit -m "Согласовать порог"

Другой способ завершить подготовленное слияние — git merge --continue. Для отказа от незавершённого слияния служит git merge --abort. Незакоммиченные изменения, существовавшие до merge, могут затруднить возврат; описанный маршрут начинается с чистых файлов и индекса. Руководство merge.

4.8 Удалённые репозитории

Действие Команда Результат
Задать имя адреса git remote add origin git@github.com:OWNER/REPOSITORY.git Локальная настройка origin
Прочитать адреса git remote -v Адреса fetch/push
Исправить существующий адрес git remote set-url origin git@github.com:OWNER/REPOSITORY.git Новый адрес того же remote
Отправить main git push -u origin main Передача объектов, обновление серверной main, настройка upstream
Получить новую копию git clone git@github.com:OWNER/REPOSITORY.git verification Новый каталог с репозиторием и рабочими файлами
Получить новые сведения git fetch origin Объекты и настроенные remote-tracking refs
Включить полученного потомка git merge --ff-only origin/main Продвижение текущей ветки при подходящем отношении истории

OWNER/REPOSITORY заменяется своим адресом. Clone запускается из родительской папки будущей копии. origin/main хранится локально и отражает полученное состояние main другого репозитория. Fetch позволяет сначала прочитать изменившийся граф; merge затем меняет текущую ветку и рабочие файлы. [2], [3]

4.9 Подготовка аккаунта

  1. Войдите в свой GitHub либо пройдите регистрацию. Подтверждение почты связывает адрес с аккаунтом.
  2. Настройте защиту входа в Settings → Password and authentication. При 2FA сохраните коды восстановления в личном защищённом хранилище.
  3. Выберите почту будущих коммитов; свой noreply доступен в настройках почты аккаунта. Проверьте git config --get user.email в проекте.
  4. Создайте пустой репозиторий через New repository. Видимость выбираете вы. При переносе готовой локальной истории оставьте создание README, лицензии и .gitignore на сервере выключенным.

Веб-вход управляет аккаунтом, SSH-ключ подтверждает аккаунт при Git-операциях, а права репозитория определяют разрешение чтения/записи.

4.10 Windows OpenSSH

Основной Windows-маршрут: системный OpenSSH и служба Windows ssh-agent. Проверка и дальнейшие команды выполняются в PowerShell 7.

$openSshDir = Join-Path $env:WINDIR 'System32/OpenSSH'
$sshClient = Join-Path $openSshDir 'ssh.exe'
$sshKeygen = Join-Path $openSshDir 'ssh-keygen.exe'
$sshAdd = Join-Path $openSshDir 'ssh-add.exe'
Test-Path -LiteralPath $sshClient
& $sshClient -V

При отсутствии клиента установите компонент OpenSSH Client по инструкции Microsoft. Установка требует прав администратора. В отдельном административном PowerShell запустите службу:

Get-Service -Name ssh-agent | Set-Service -StartupType Manual
Start-Service ssh-agent
Get-Service ssh-agent

Ожидается Running. С режимом Manual после остановки или перезагрузки может понадобиться новый запуск службы. В обычном пользовательском PowerShell проверьте прежний выбор ssh и при переходе на системный клиент сохраните согласованную команду для Git:

git config --global --get core.sshCommand
$sshProgram = '"' + $sshClient.Replace('\', '/') + '"'
git config --global core.sshCommand $sshProgram
git config --show-origin --get core.sshCommand

--global относится ко всем репозиториям пользователя. --show-origin показывает, из какого файла взялось действующее значение в текущем проекте. Настройки репозитория и переменные GIT_SSH/GIT_SSH_COMMAND могут влиять на выбор команды. При несовпадении клиента проверьте их и прежнюю настройку перед изменением. Git for Windows и Windows OpenSSH могут использовать разные агенты. Документация GitHub.

4.11 Выбор ключа

В PowerShell прочитайте имена файлов в $HOME/.ssh; в fish — в ~/.ssh. Открытая часть пары имеет окончание .pub. Существующий подходящий ключ можно использовать повторно. Для новой пары сначала проверьте свободное имя обоих файлов.

PowerShell, после настройки системного клиента:

Get-ChildItem -Force -LiteralPath "$HOME/.ssh"
New-Item -ItemType Directory -Force -Path "$HOME/.ssh"
$keyPath = Join-Path $HOME '.ssh/id_ed25519_course'
Test-Path -LiteralPath $keyPath
Test-Path -LiteralPath "$keyPath.pub"

Если каталога ещё нет, первая команда сообщит об отсутствии. Для нового имени два Test-Path должны вернуть False. Только для свободного имени:

& $sshKeygen -t ed25519 -C 'course-computer' -f $keyPath

При существующей паре задайте $keyPath её фактическим путём. Добавление выбранного ключа в работающий агент:

& $sshAdd $keyPath
& $sshAdd -l
Get-Content -Raw -LiteralPath "$keyPath.pub"

При создании задаётся парольная фраза; ssh-add запрашивает её для открытия ключа. -l показывает отпечатки доступных агенту ключей. Последняя команда читает открытую часть для регистрации в GitHub.

4.12 Ключ в fish/Linux

ssh -V
ssh-add -l
ls -la ~/.ssh

При доступном агенте можно продолжать с ним. Если агент отсутствует, команда ssh-agent fish откроет вложенный fish с доступом к новому агенту; этот агент завершится при выходе из вложенного сеанса.

ssh-agent fish
mkdir -p ~/.ssh
test -e ~/.ssh/id_ed25519_course
echo $status
test -e ~/.ssh/id_ed25519_course.pub
echo $status

У test код 0 означает существующий путь. Для занятого имени выбирается другое; генерация выполняется только для двух свободных путей:

ssh-keygen -t ed25519 -C 'course-computer' -f ~/.ssh/id_ed25519_course
ssh-add ~/.ssh/id_ed25519_course
ssh-add -l
cat ~/.ssh/id_ed25519_course.pub

Для уже существующей пары используйте её путь в ssh-add и cat; генерация пропускается. Закрытая часть используется локально, открытая добавляется в аккаунт.

4.13 Проверка доступа

В GitHub откройте Settings → SSH and GPG keys → New SSH key. Задайте понятное название компьютера, выберите Authentication и вставьте полный текст выбранного .pub. Регистрация ключа.

PowerShell с выбранным системным клиентом:

& $sshClient -T git@github.com
$LASTEXITCODE

Fish:

ssh -T git@github.com
echo $status

Первое доверие серверу подтверждается после сверки типа и полного отпечатка с официальной страницей. При несовпадении соединение прерывают и выясняют причину. Ожидаемое сообщение называет аккаунт и успешную аутентификацию, затем отсутствие shell-доступа. У GitHub этот тест штатно заканчивается кодом 1. Push дополнительно проверяет право записи в выбранный репозиторий. Проверка SSH.

4.14 Диагностика обмена

Наблюдение Проверка
Агент недоступен Windows: состояние службы и выбранный ssh-add; fish: окружение сеанса, запущенного под агентом
Permission denied (publickey) Наличие нужного ключа в агенте, открытый ключ в ожидаемом аккаунте, выбранный клиент
SSH приветствует другой аккаунт Какой ключ использован и в каком аккаунте он зарегистрирован
Ключ сервера отличается от доверенного Адрес сервера, официальный отпечаток, причина изменения; соединение остаётся остановленным до выяснения
Repository not found OWNER/REPOSITORY, существование репозитория, права распознанного аккаунта
remote origin already exists Прочитать remote -v; исправить адрес существующего origin при необходимости
Push отклонён как non-fast-forward Получить историю fetch, прочитать обе линии, интегрировать полезные изменения

4.15 Упаковка результата

Полный локальный результат включает файлы, индекс, ссылки и историю в .git. Для сдачи используется каталог versioning с двумя обычными репозиториями и explanation.md. Завершите операции Git и редактирование перед созданием архива. Команды выполняются из родительской папки versioning; выходной архив находится рядом с ним.

PowerShell 7 использует штатный API .NET, включающий скрытое содержимое:

$source = (Resolve-Path -LiteralPath './versioning').Path
$archive = Join-Path (Get-Location).Path 'version-control.zip'
[System.IO.Compression.ZipFile]::CreateFromDirectory(
    $source, $archive,
    [System.IO.Compression.CompressionLevel]::Optimal, $true
)

$source и $archive содержат абсолютные пути. Последний аргумент $true включает корневое имя versioning в ZIP. Выходное имя должно быть свободно; существующий архив вызывает исключение. При повторной сдаче выберите новое имя либо уберите собственный предыдущий архив после проверки нужной версии. ZipFile.CreateFromDirectory.

Compress-Archive исключает скрытые файлы и каталоги. Его обычный вызов может потерять .git; для репозиториев применяется показанный API .NET. Описание Compress-Archive.

Fish/Linux с GNU tar:

tar -czf version-control.tar.gz versioning
tar -tzf version-control.tar.gz

-c создаёт архив, -z включает gzip, -f задаёт имя файла; -t перечисляет содержимое. Передаётся сам каталог versioning, поэтому рекурсивно включаются его обычные и скрытые файлы. В списке должны присутствовать оба .git/HEAD и объектные данные .git.

Извлеките собственный архив в новую папку archive-check. Для ZIP в PowerShell:

Expand-Archive -LiteralPath ./version-control.zip -DestinationPath ./archive-check

-LiteralPath задаёт буквальный путь ZIP. Отсутствующая папка назначения создаётся при извлечении; существующие файлы без -Force сохраняются. Expand-Archive.

Для tar.gz в fish:

mkdir archive-check
tar -xzf version-control.tar.gz -C archive-check

Затем в любой из двух оболочек:

git -C archive-check/versioning/project rev-parse HEAD
git -C archive-check/versioning/project log --oneline --all
git -C archive-check/versioning/project status --short
git -C archive-check/versioning/verification rev-parse HEAD
git -C archive-check/versioning/verification status --short

Идентификаторы должны совпасть с упакованными вершинами, история — содержать нужные исходные коммиты и слияние, оба статуса — быть чистыми. Проверьте также восстановленные файлы.
