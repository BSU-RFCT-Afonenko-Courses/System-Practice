Распределённая история

Git — распределённая система управления версиями: обычная полная копия проекта содержит собственный репозиторий с историей.

локальный репозиторий <── обмен ──> другой репозиторий
сохранение и чтение истории         своя история и ссылки

Локальные состояния сохраняются без сервера. Общий сервер может служить местом обмена. Передача изменений требует отдельной операции.

Возникновение Git

Git создан в 2005 году для разработки ядра Linux после использования BitKeeper. Для этого проекта были существенны:

  • собственные репозитории разработчиков;
  • частое объединение подготовленных изменений;
  • скорость операций над большой историей;
  • целостность сохранённых данных.

Свидетельство Linus Torvalds.

Снимок проекта

Снимок задаёт содержимое отслеживаемых файлов в выбранном состоянии. Коммит связывает снимок с сообщением, автором и родителями — непосредственными предшественниками в истории.

коммит B ──> снимок: criteria=12, README, measurements
    │
    v
родитель A ─> снимок: criteria=10, README, measurements

Начальный коммит имеет ноль родителей; обычное продолжение — одного. Различие между A и B получается сравнением двух снимков. [1, сс. 66–68]

Показать неизменившиеся README и measurements в обоих снимках. Спросить, потеряны ли они при изменении одной строки criteria. Проследить отдельно ссылку на снимок и ссылку на родителя.

Рабочее состояние

Рабочее дерево — файлы проекта, доступные редактору и программам. Индекс — содержимое, подготовленное для следующего снимка. В обычном локальном репозитории .git хранит служебные данные Git.

редактор           git add            git commit
рабочие файлы ─────────────> индекс ─────────────> коммит

Сохранение файла редактором меняет рабочее дерево. Подготовка выбирает содержимое, которое затем сохранит обычный commit.

Попросить указать действие, выполняемое привычным сочетанием Ctrl+S. Спросить, какая стрелка нужна после редактирования, чтобы выбрать файл для следующего коммита.

Текущая ветка

Ветка — именованная изменяемая ссылка на коммит. HEAD в обычной работе указывает на текущую ветку.

После сохранения первого снимка A:

HEAD ──> main ──> A
                 │
                 порог 10 ms

После обычного нового коммита перемещается текущая ветка. Идентификатор коммита вычисляется из его данных; буква A обозначает выбранный коммит на этой схеме.

Прочитать схему ожидаемого результата от HEAD к снимку. Попросить назвать, какая часть схемы должна измениться при следующем commit. После начального сохранения сопоставить реальный ID с буквой A.

Начальная история

В корне latency-demo:

git init -b main
git config user.name "Ваше имя"
git config user.email "YOUR_EMAIL"
git add -- README.md criteria.txt measurements.tsv
git commit -m "Сохранить исходные измерения"

Имя и почта заменяются собственными значениями. Они входят в коммиты. main — начальная ветка. Первый коммит A содержит три исходных файла.

Показать status до add и после commit. Объяснить неотслеживаемые файлы через отсутствие в подготовленном снимке. Уточнить область локальной конфигурации и отличие сведений автора от проверки доступа к серверу.

Подготовка значения

HEAD/A содержит порог 10 ms. Измените рабочую строку на 12 ms.

PowerShell 7:

Set-Content -LiteralPath criteria.txt -Value 'latency_limit = 12 ms'

Fish:

printf '%s\n' 'latency_limit = 12 ms' > criteria.txt
git add -- criteria.txt

Теперь индекс хранит 12 ms, сохранённый A — 10 ms.

Исполнить только маршрут выбранной ОС. Показать рабочий файл и diff –staged. Уточнить, что add подготавливает содержимое именно на момент вызова; последующий прогноз сделать до следующей правки.

Неподготовленное изменение

После add рабочий файл изменён ещё раз, до latency_limit = 20 ms.

Место Порог

Индекс 12 ms

Два сравнения

Индекс совпадает с B: 12 ms. Рабочий эксперимент сохраняет 20 ms. Статус M criteria.txt показывает оставшееся рабочее изменение. Стрелка B → A указывает непосредственного родителя B.

Восстановление рабочего файла

Незакоммиченный эксперимент 20 заменён; статус пуст. Полезные рабочие правки сохраняют до такой замены.

Новая ветка

Предок достижим последовательными переходами по родителям. В цепочке C → B → A коммит B — родитель C, а коммит A — предок C.

git branch source-note
git switch source-note
HEAD ──> source-note ──> B ──> A
                        ^
                 main ──┘

Создание ветки добавило ссылку. Переключение выбрало её через HEAD. Обе ссылки пока указывают на B с порогом 12 ms.

Показать два шага отдельно и спрашивать о положении HEAD после каждого. Предложить посчитать коммиты до и после branch. Связать отсутствие нового коммита с неизменностью снимка.

Продолжение выбранной линии

В README.md добавлена строка о происхождении учебных измерений.

git add -- README.md
git commit -m "Указать происхождение измерений"
HEAD ──> source-note ──> C ──> B ──> A
                             ^
                      main ──┘

Новый C содержит дополненное описание. Продвинулась source-note; main сохранила ссылку на B.

Попросить объяснить неизменность main. В C отдельно прочитать criteria.txt: порог остался 12. Уточнить, что изменение одного файла создаёт снимок всего отслеживаемого проекта.

Возврат к основной ветке

git switch main

HEAD выбирает main/B. При чистом состоянии индекс и рабочие файлы обновляются по B. Строка происхождения исчезает из рабочего README.md.

main/B: прежний README      source-note/C: README с источником

C сохраняется в репозитории через source-note. Выбор его ветки снова даст дополненное описание.

Fast-forward

main/B является предком C. Fast-forward перемещает ветку к существующему потомку без нового коммита.

git merge --ff-only source-note
HEAD ──> main ────────┐
                     v
                     C ──> B ──> A
                     ^
         source-note ┘

Описание из C теперь находится в основной ветке и рабочих файлах.

Сопоставить число коммитов до и после операции. Показать, что непосредственное родительство не обязательно: допустима и цепочка из нескольких коммитов между исходной и новой вершинами.

Независимые требования

Общее состояние C содержит порог 12 ms. Появились два изменения:

Линия Требование Будущий критерий
main Повысить порог 20 ms
seconds Выразить исходный порог в секундах 0.012 s

Рабочая ветка создаётся от C:

git switch -c seconds

В неё войдут новая запись критерия и пояснение единицы в README.md.

Проверить равенство 12 ms и 0.012 s. Спросить, меняет ли второе требование физическую величину порога. Уточнить исходную точку C до редактирования каждой линии.

Две вершины истории

В seconds создан S с 0.012 s и пояснением в README.md. После возврата к main/C создан T с 20 ms.

HEAD ──> main ──> T ──┐
                     v
                     C ──> B ──> A
                     ^
       seconds ──> S ┘

У T и S общий родитель C. Ни одна вершина не является предком другой: линии расходятся. Fast-forward для их соединения невозможен.

Трёхстороннее слияние

Слияние сопоставляет общий исходный снимок с изменениями двух линий.

Файл C, общее начало T, main S, seconds
criteria.txt 12 ms 20 ms 0.012 s
README.md Исходное описание То же Добавлена единица порога

README.md соединяется автоматически. Обе линии изменили одну строку criteria.txt; Git останавливается для её разрешения.

Конфликт

Конфликт слияния требует выбрать согласованное содержимое файла. Рабочий criteria.txt содержит:

<<<<<<< HEAD
latency_limit = 20 ms
=======
latency_limit = 0.012 s
>>>>>>> seconds

Верхняя часть относится к текущей main/T, нижняя — к seconds/S. main пока остаётся на T. Индекс отмечает неразрешённый конфликт.

Прочитать происхождение каждой части по графу. Попросить сформулировать оба требования словами, прежде чем удалять строки. Уточнить, что метки обозначают стороны текущей операции.

Согласованное значение

Новый порог равен 20 ms, выбранная единица записи — секунда. Из 1000 ms = 1 s следует:

latency_limit = 0.020 s

После замены конфликтного блока и проверки README.md:

git commit -m "Согласовать порог"

Add подготавливает принятое содержимое; commit завершает слияние.

Коммит слияния

HEAD ──> main ──> M ──> T ──┐
                 │         v

M содержит порог 0.020 s и имеет родителей T и S. Обе линии достижимы из main; рабочие файлы и индекс совпадают с M.

Две строки parent называют непосредственных родителей M.

Удалённый репозиторий

GitHub — сервис размещения репозиториев и управления доступом к ним. Локальная main/M готова к передаче в собственный учебный репозиторий.

локальная копия ── отправка ──> GitHub ── получение ──> новая копия

Веб-интерфейс управляет аккаунтом, репозиторием и доступом. GitHub CLI gh предоставляет командный интерфейс к возможностям GitHub. Новая локальная копия получает собственные файлы, индекс и ссылки.

Попросить назвать, какая сторона хранит собственный индекс для работы редактора. Спросить, достаточно ли локального commit, чтобы данные появились в веб-интерфейсе GitHub.

Способы соединения

Способ Свойство
Локальный путь Доступ к репозиторию через файловую систему
HTTPS Защищённый канал; Git Credential Manager поддерживает браузерный вход GitHub
SSH Защищённый канал; доступ GitHub по пользовательскому ключу
git:// Без встроенного шифрования и аутентификации

GitHub отключил git:// 15 марта 2022 года. Public/private определяет доступ к размещённым файлам. Шифрование канала защищает данные при передаче.

Пользовательская пара ключей

Закрытый ключ создаёт подпись; открытый позволяет её проверить. В аккаунт GitHub добавляется открытый файл .pub с типом Authentication. Закрытый ключ остаётся на компьютере пользователя.

Парольная фраза защищает сохранённый ключ. Агент SSH предоставляет клиенту возможность выполнять подписи доступным ему ключом.

Существующие ключи сохраняются. Новая пара получает свободное имя. OpenSSH реализует протокол SSH. На Windows Git использует согласованный системный OpenSSH и службу агента Windows.

В Git сохраняется текстовый указатель: версия формата, SHA-256 и размер. Содержимое большого файла размещается отдельно и получается клиентом LFS.

Нагрузка репозитория

Стоимость операций зависит от:

  • объёма истории и рабочих файлов;
  • частоты сохранения и отправки изменений;
  • числа одновременных чтений;
  • конкуренции обновлений одной общей ветки.

CI — автоматическая сборка и проверки — может многократно запрашивать один снимок. Постоянное соединение клиентов с сервером даёт другие возможности размещения данных, чем автономная работа полной копии.

Scion в Anthropic

Anthropic, 13.10.2026; обновление 15.10: огромный собственный монорепозиторий, постоянно подключённые задания и агенты, частые изменения и получение рабочих файлов.
