История проекта измерений

Состояния проекта

  • Локальная история проекта измерений.
  • Подготовка снимка. Чтение сохранённых состояний.
  • Развитие веток. Интеграция расходящихся изменений.
  • Настройка SSH. Обмен через свой репозиторий GitHub.
  • Проверка истории во второй копии.

Команды выполняются в выбранном маршруте: PowerShell 7/Windows либо fish/Linux.

Восстановить по памяти три состояния файла: сохранённое, подготовленное, рабочее. Попросить привести знакомый пример копирования каталога перед экспериментом и назвать сведения, которые должна сохранить история.

Исходные файлы

Распакуйте демонстрационный архив в новую папку. В latency-demo три обычных файла; .git ещё отсутствует.

Файл Назначение
criteria.txt Порог latency_limit = 10 ms
measurements.tsv Измерения north — 8 ms, south — 18 ms
README.md Описание данных и включения измерений в отчёт

Откройте файлы редактором. При пороге 10 ms проходит запись north. Перейдите в latency-demo в PowerShell 7 либо fish.

Проверить текущую папку и прочитать три файла. Восстановить знакомую операцию копирования проекта перед изменением. Попросить объяснить, какая запись проходит исходный критерий.

Аккаунт проекта

Для собственного удалённого репозитория используется личный аккаунт GitHub. Войдите в существующий аккаунт либо пройдите регистрацию, подтвердите почту.

Настройте защиту входа в Settings → Password and authentication. При 2FA коды восстановления сохраняются в личном защищённом хранилище.

Для коммитов можно выбрать подтверждённую почту или свой GitHub noreply из настроек почты. Этот адрес будет виден читателям истории.

Пользователь сам выполняет вход и настройку. Секретные поля и коды восстановления на общий экран не выводятся. Спросить, почему выбор почты следует сделать до сохранения истории для публикации.

Локальный репозиторий

В корне latency-demo:

git --version
git init -b main
git config user.name "Ваше имя"
git config user.email "YOUR_EMAIL"
git config --get user.name
git config --get user.email

Подставьте своё имя и выбранный адрес. Настройка без --global относится к этой папке. Init создаёт .git и начальную ветку main; сохранённых коммитов ещё нет.

Показать status после init: три неотслеживаемых файла. Уточнить, что имя и почта являются сведениями автора в будущих коммитах. Проверка доступа к GitHub выполняется при отдельном соединении.

Первый снимок

Рабочее дерево содержит редактируемые файлы. Индекс хранит подготовленное содержимое будущего снимка. [@bib-chacon-straub-progit, с. 22–39]

git add -- README.md criteria.txt measurements.tsv
git --no-pager diff --staged
git commit -m "Сохранить исходные измерения"
git status --short

Сохранён коммит A: порог 10 ms и два остальных исходных файла. Ветка main указывает на A; HEAD выбирает main. Пустой статус подтверждает совпадение рабочего дерева и индекса с A.

Перед commit прочитать подготовленные файлы. Найти идентификатор A в выводе и записать его для чтения истории. Попросить назвать действие, которое изменило индекс, и действие, которое создало коммит.

Подготовленный порог

PowerShell 7:

Set-Content -LiteralPath criteria.txt -Value 'latency_limit = 12 ms'

Fish:

printf '%s\n' 'latency_limit = 12 ms' > criteria.txt

В выбранной оболочке затем:

git add -- criteria.txt
git --no-pager diff --staged

Индекс хранит 12 ms; HEAD/A сохраняет 10 ms.

Попросить предсказать строки со знаками минус и плюс. Установить момент, в который add прочитал файл. Выполнять команды изменения содержимого только из варианта своей оболочки.

Рабочий эксперимент

Какое значение сохранит обычный commit после следующей правки?

Измените строку ещё раз на latency_limit = 20 ms в редакторе или соответствующей команде записи своей оболочки.

git status --short
git --no-pager diff -- criteria.txt
git --no-pager diff --staged -- criteria.txt
HEAD Индекс Рабочий файл
10 ms 12 ms 20 ms

Статус — MM. Обычный diff показывает 12 → 20, подготовленный diff — 10 → 12.

До выполнения следующего commit попросить прогноз сохранённой величины. При ответе 20 прочитать подготовленный diff. После уточнения прогноза продолжить опыт без повторного add.

Сохранение выбранного значения

git commit -m "Уточнить порог до 12 ms"
git show 'HEAD:criteria.txt'
git status --short

Коммит B содержит 12 ms, его родитель — A. Рабочий файл сохраняет 20, поэтому короткий статус — M criteria.txt.

Для завершения эксперимента восстановите файл из индекса:

git restore -- criteria.txt

Рабочее дерево, индекс и HEAD/B теперь содержат 12 ms.

Прочитать рабочий diff до восстановления. Получить осознанное решение о завершении экспериментальной правки. После restore показать пустой status и назвать источник восстановленного файла — индекс.

Линия описания

git switch -c source-note

В README.md добавьте строку Источник: учебные измерения двух датчиков.

git add -- README.md
git commit -m "Указать происхождение измерений"
HEAD ──> source-note ──> C ──> B ──> A
                             ^
                      main ──┘

Новая ветка продолжила B. main осталась на прежнем снимке.

Попросить указать новую строку только в снимке C. Сопоставить создание ветки и создание коммита: первое добавило имя, второе — снимок с родительской связью.

Продвижение main

git switch main

README.md снова соответствует B: строки происхождения нет. Для включения готового описания:

git merge --ff-only source-note

main перемещается B → C по существующей истории. Нового коммита нет; рабочий README.md снова содержит строку происхождения. Это fast-forward: исходная вершина была предком новой.

Показывать содержимое между двумя командами. Спросить, где хранилась строка во время возврата к B. После merge сравнить число коммитов и положение ссылок в log –graph –decorate –all.

Запись в секундах

На main/C порог равен 12 ms:

git switch -c seconds

Измените criteria.txt на latency_limit = 0.012 s. Дополните README.md строкой Порог в criteria.txt выражен в секундах.

git add -- criteria.txt README.md
git commit -m "Выразить порог в секундах"

Коммит S сохраняет величину 12 ms в другой единице. Данные measurements.tsv продолжают выражаться в миллисекундах.

Проверить соотношение единиц перед add. Попросить прочитать оба подготовленных файла как одно согласованное изменение. Указать S в decorated log и его родителя C.

Изменение основной линии

git switch main

Рабочие файлы возвращаются к C. Измените criteria.txt на latency_limit = 20 ms, затем:

git add -- criteria.txt
git commit -m "Повысить порог до 20 ms"
main ──> T ──> C <── S <── seconds

T и S расходятся от C. Новое требование main меняет величину порога.

Попросить прочитать путь от каждой вершины к C. Проверить отсутствие пути от T к S по родителям. Сопоставить физический смысл каждого из двух изменений до запуска merge.

Остановка на конфликте

На main/T с чистым статусом:

git merge seconds

Рабочий criteria.txt:

<<<<<<< HEAD
latency_limit = 20 ms
=======
latency_limit = 0.012 s
>>>>>>> seconds

main остаётся на T. README.md получил совместимое пояснение из S.

Прочитать status и найти конфликтный путь. Спросить, какой коммит задаёт каждую сторону блока. Показать автоматически соединённый README и сохранить оба требования к критерию на доске.

Разрешение по требованиям

Какой критерий одновременно выполняет оба требования?

Нужно сохранить новый порог 20 ms и выражать его в секундах. Весь конфликтный блок заменяется на:

latency_limit = 0.020 s
git add -- criteria.txt
git --no-pager diff --staged
git commit -m "Согласовать порог"

Коммит M имеет родителей T и S. Маркеры конфликта удалены, README.md поясняет секунды, исходные данные сохранились.

Попросить объяснить итог через 1000 ms = 1 s. Проверить обе стороны требования после редактирования. Прочитать staged diff относительно T, затем получить два parent в raw-описании M.

Проверка локальной истории

git --no-pager log --graph --oneline --decorate --all
git --no-pager show --no-patch --format=raw HEAD
git show 'HEAD:criteria.txt'
git status --short
main ──> M ──> T ──> C ──> B ──> A
         │           ^
         └──> S ─────┘
              ^
     seconds ─┘

Ожидаются M с двумя родителями, порог 0.020 s и чистое рабочее состояние.

Попросить найти A по связям из M. Проверить порог, единицу и исходные измерения. Найти в графе происхождение изменений, а в criteria.txt — выбранную величину порога и её единицу.

Проверка Windows OpenSSH

В пользовательском PowerShell 7:

$openSshDir = Join-Path $env:WINDIR 'System32/OpenSSH'
$sshClient = Join-Path $openSshDir 'ssh.exe'
$sshKeygen = Join-Path $openSshDir 'ssh-keygen.exe'
$sshAdd = Join-Path $openSshDir 'ssh-add.exe'
Test-Path -LiteralPath $sshClient
& $sshClient -V

Ожидаются True и версия системного OpenSSH. При отсутствии клиента установите компонент OpenSSH Client по инструкции Microsoft.

Fish/Linux использует ssh -V; его маршрут агента приведён отдельно ниже.

Сопоставить фактический путь с выбранным системным клиентом. Показать результат Test-Path и версию запущенного ssh.exe. Попросить назвать программу, к которой относится наблюдаемый вывод.

Агент Windows

В отдельном PowerShell с правами администратора:

Get-Service -Name ssh-agent | Set-Service -StartupType Manual
Start-Service ssh-agent
Get-Service ssh-agent

Ожидается Running. При Manual после остановки/перезагрузки службу может потребоваться запустить снова.

Далее вернитесь в обычный пользовательский PowerShell. Агент предоставляет клиенту возможность подписывать запросы доступным ключом. Добавление личного ключа выполняется от своего пользователя.

Различить административную настройку службы и пользовательскую работу с ключом. Показать состояние службы. Уточнить, в каком окне сохранены переменные openSshDir и sshClient предыдущего шага.

Выбор клиента Git

В обычном PowerShell прочитайте прежнюю настройку:

git config --global --get core.sshCommand

При переходе на системный Windows OpenSSH:

$sshProgram = '"' + $sshClient.Replace('\', '/') + '"'
git config --global core.sshCommand $sshProgram
git config --show-origin --get core.sshCommand

Проверьте совпадение действующего пути Git с выбранным системным клиентом. Глобальная настройка относится к репозиториям текущего пользователя.

Прочитать прежнее значение до изменения. При переопределении локальной конфигурацией или GIT_SSH_COMMAND разобрать источник по справочнику. Сопоставить путь проверочной программы со значением, полученным из конфигурации Git.

Выбор пары ключей

PowerShell:

Get-ChildItem -Force -LiteralPath "$HOME/.ssh"

Fish:

ls -la ~/.ssh

Открытый файл имеет окончание .pub, закрытый остаётся на компьютере. Существующую пригодную пару можно использовать. Для новой пары выберите свободное имя обоих файлов, например id_ed25519_course. Отсутствие каталога команда покажет сообщением.

Пользователь рассматривает имена своих файлов без чтения закрытого содержимого. Попросить объяснить назначение расширения .pub. При существующей настройке выбрать её путь перед вызовом ssh-add.

Новая пара в PowerShell

New-Item -ItemType Directory -Force -Path "$HOME/.ssh"
$keyPath = Join-Path $HOME '.ssh/id_ed25519_course'
Test-Path -LiteralPath $keyPath
Test-Path -LiteralPath "$keyPath.pub"

Для новой пары оба результата должны быть False. Только при свободном имени:

& $sshKeygen -t ed25519 -C 'course-computer' -f $keyPath
& $sshAdd $keyPath

Задайте парольную фразу. Для существующего ключа задайте его путь в keyPath и выполните только ssh-add.

До генерации проверить оба результата Test-Path. Объяснить подпись -C как узнаваемую метку устройства и -f как выбор файла. Парольную фразу пользователь вводит самостоятельно без сохранения в учебном отчёте.

Агент fish/Linux

ssh -V
ssh-add -l

При доступном агенте можно использовать его. Если агент отсутствует:

ssh-agent fish

Откроется вложенный fish с адресом нового агента в окружении. Работа с ключом и Git продолжается в этом сеансе. Его exit завершит запущенный для него агент.

Сопоставить сообщения о пустом агенте и о недоступном агенте. При демонстрации нового агента отметить вложенность оболочки. Спросить, в каком процессе будут доступны его переменные окружения.

Новая пара в fish

mkdir -p ~/.ssh
test -e ~/.ssh/id_ed25519_course
echo $status
test -e ~/.ssh/id_ed25519_course.pub
echo $status

Код 0 у test означает занятое имя. Для двух свободных путей:

ssh-keygen -t ed25519 -C 'course-computer' -f ~/.ssh/id_ed25519_course
ssh-add ~/.ssh/id_ed25519_course

Для существующей пары используется её путь в ssh-add; генерация пропускается.

Вывести $status сразу после соответствующего test. При занятом имени выбрать новое и повторить обе проверки. Объяснить работу парольной фразы при создании ключа и его добавлении в агент.

Открытый ключ в аккаунте

Прочитайте .pub выбранной пары. PowerShell:

Get-Content -Raw -LiteralPath "$keyPath.pub"

Fish:

cat ~/.ssh/id_ed25519_course.pub

В GitHub: Settings → SSH and GPG keys → New SSH key. Выберите Authentication, название компьютера и вставьте полный открытый ключ. Он позволит серверу проверить подпись клиента.

Сопоставить открытый ключ с путём закрытой части, загруженной в агент. Пользователь самостоятельно подтверждает добавление в аккаунт. Попросить назвать данные, которые сервер получает для проверки.

Ключ сервера

PowerShell с выбранным клиентом:

& $sshClient -T git@github.com

Fish:

ssh -T git@github.com

При первом запросе доверия сверяйте тип и полный отпечаток с официальной страницей GitHub. Подтвердите yes только после совпадения. При различии остановите соединение и выясните причину.

Различить ключ сервера и пользовательскую пару. Показать, какую строку официального списка выбирают по типу предложенного ключа. Установить, что последующие подключения сверяются с сохранённым known_hosts.

Результат аутентификации

GitHub должен назвать ожидаемый аккаунт:

Hi USERNAME! You've successfully authenticated, but GitHub does not provide shell access.

Сразу после ssh в PowerShell прочитайте $LASTEXITCODE, в fish — echo $status. Штатный код этого теста GitHub — 1: сервис подтвердил аутентификацию и завершил соединение без shell.

Право записи в конкретный репозиторий проверяется при push. Закрытый ключ остаётся локальным; сеансовые ключи защищают передачу.

Если показан другой аккаунт, вернуться к выбранной паре и её регистрации. При Permission denied (publickey) проверить агент, клиент и открытый ключ. Сопоставить успешное сообщение с назначением ssh -T у GitHub.

Пустой репозиторий GitHub

Создайте New repository в своём аккаунте. Выберите имя и видимость Public либо Private. README, лицензию и .gitignore при создании оставьте выключенными: первая отправка принесёт готовую локальную историю.

В latency-demo подставьте SSH-адрес созданного репозитория:

git remote add origin git@github.com:OWNER/REPOSITORY.git
git remote -v
git push -u origin main

origin — локальное имя адреса. Push передаёт историю и обновляет серверную main; -u задаёт upstream для локальной main.

Проверить owner/name и фактическую видимость. После push открыть серверную историю, найти M и criteria.txt с 0.020 s. Если origin уже существует, сначала прочитать его адрес и действовать по справочнику.

Вторая копия

Перейдите в родительскую папку latency-demo. Имя latency-check свободно:

git clone git@github.com:OWNER/REPOSITORY.git latency-check

В новой папке latency-check:

git rev-parse HEAD
git remote -v
git --no-pager log --graph --oneline --decorate --all
git status --short

Получена своя main/M, собственные индекс и рабочие файлы. ID M совпадает с отправленным, порог равен 0.020 s, статус чист.

Сравнить данные обеих папок. Найти родителей M в полученной истории. Попросить объяснить отличие нового репозитория от одного скачанного файла criteria.txt через доступные наблюдения log и status.

Изменение второй копии

В latency-check проверьте имя и почту автора. Локальная настройка первой папки не переносится при clone; задайте нужные значения здесь.

Добавьте в README.md строку Проверка: данные прочитаны во второй копии.

git add -- README.md
git commit -m "Отметить проверку второй копии"
git push origin main

Новый N имеет родителя M. Серверная main теперь выбирает N; первая копия сохраняет прежние сведения до обмена.

Проверить git config –get user.name и user.email перед commit. Зафиксировать ID N. Попросить предсказать содержимое README в первой папке и проверить его до fetch.

Fetch в первой копии

Вернитесь в latency-demo:

git fetch origin
git --no-pager log --graph --oneline --decorate --all
origin/main ──> N ──> M
                     ^
              main ──┘

origin/main — локальная ссылка на полученное состояние серверной main. Fetch обновил её до N; собственная main и рабочий README пока сохраняют M.

Прочитать show origin/main:README.md и сравнить с рабочим файлом. Попросить объяснить два результата через разные ссылки на схеме. Отметить, какая часть операции уже потребовала сети.

Включение полученной истории

В latency-demo:

git merge --ff-only origin/main
git rev-parse HEAD
git show 'HEAD:criteria.txt'
git status --short

main продвинулась M → N, рабочий README получил строку проверки. criteria.txt сохраняет 0.020 s, история — оба родителя M.

В справочнике упаковки приведены сохранение .git и проверка архива. Самостоятельная работа задаёт свойства собственного проекта, истории и внешнего обмена.

Попросить разделить наблюдаемые эффекты fetch и merge. Сопоставить вершины и файлы двух копий после включения N. Для дальнейшей работы открыть самостоятельное условие и прочитать его исходные значения.
