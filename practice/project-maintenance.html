Подготовка выпуска

Подготовка выпуска

  • Проверка сохранённой версии проекта.
  • Получение следующего изменения.
  • Применение патча к исходному тексту.
  • Именование проверенного снимка.
  • Передача истории и материалов выпуска.

Знакомый проект измерений сохраняет порог 0.020 s и две исходные записи. Как передать проверенную версию, к которой можно обратиться позднее? Опыт выполняется в одной среде: PowerShell 7/Windows либо fish/Linux.

Попросить восстановить различие main, коммита и рабочего файла. Назвать задачу получателя: открыть именно проверенную версию после следующего изменения проекта. Связать её с устойчивым именем выпуска.

Состояние N

Распакуйте демонстрационный архив в новую папку. В maintenancelab/work сохранена знакомая история:

main, start ──> N ──> M ──> T ──> C
                     │           ^
                     └──> S ─────┘

N содержит README.md, criteria.txt с 0.020 s и исходные measurements.tsv: north — 8 ms, south — 18 ms. Индекс и рабочие файлы чисты. В README сохранена строка проверки второй копии. Тег start задаёт имя исходного N; новые коммиты ветки сохраняют его на этой версии.

Найти в графе родителей M и объяснить согласованный порог. Показать реальные ID, соответствующие обозначениям схемы. Сопоставить измерения в ms с порогом в s.

Репозитории опыта

В каком хранилище уже есть новая проверка U?

maintenancelab/
├── work/             рабочее дерево, индекс, история .git
├── shared.git/       объекты и ссылки без рабочего дерева
└── incoming/
    └── guide.patch   дополнение README.md

В shared.git main выбирает U, родитель которого — N. U добавляет CHECKS.md; остальные файлы сохранились. Откройте терминал в work. Связь с shared.git задаётся локальным путём.

Попросить найти текущий каталог и отличить обычный репозиторий от bare. Проверить наличие входного патча. Спросить, почему до fetch в work может отсутствовать коммит, уже сохранённый в shared.git.

Исходное наблюдение

Как установить текущую версию и наличие несохранённых изменений?

В work задайте собственные данные автора:

git config user.name "Ваше имя"
git config user.email "YOUR_EMAIL"
git status --short
git --no-pager log --graph --oneline --decorate --all

Ожидаются main/N, start/N и чистый статус. Локальная настройка автора относится к этому репозиторию. Имя и почта войдут в новые коммиты.

Проверить исходную вершину перед продолжением. При непустом статусе сначала установить происхождение правок. Попросить прочитать из N criteria.txt и объяснить единицу сохранённого значения.

Соседняя версия

Как прочитать M, сохранив текущую main/N?

git worktree add --detach ../previous HEAD~1
git worktree list
git -C ../previous show 'HEAD:README.md'
git show 'HEAD:README.md'

HEAD~1 выбирает родителя N; -C задаёт каталог команды. У previous собственные файлы, индекс и HEAD/M; объекты и обычные refs общие. В старом README ещё нет строки проверки.

Предложить мысленный опыт: в рабочий README папки previous добавили строку без создания коммита. Попросить определить, появится ли она в выводе show ‘HEAD:README.md’, и указать источник чтения. Объяснить –detach через прямую ссылку HEAD на M. По worktree list проверить, что основная main осталась на N.

Завершение просмотра

Какое состояние позволяет удалить дополнительное дерево после чтения?

git -C ../previous status --short
git worktree remove ../previous
git worktree list

После чтения статус previous пуст. Remove удаляет чистое связанное дерево. Основная история и файлы work сохраняются.

Файл .git внутри previous указывал на служебные данные этого дерева. Они и общая база объектов расположены вне previous. Перенос одной связанной папки оставил бы зависимость от этих внешних данных.

До remove показать файл .git в дополнительной папке без изменения его содержимого. Попросить объяснить, какие данные требуются для самостоятельного чтения истории после переноса на другой компьютер.

Получение U

Как прочитать U до изменения собственной main?

git remote add origin ../shared.git
git fetch origin
git --no-pager log --graph --oneline --decorate --all
git show 'origin/main:CHECKS.md'
origin/main ──> U ──> N <── main, start

Fetch получил U и обновил origin/main. Рабочая папка пока соответствует N. CHECKS.md проверяет 0.008 s и 0.018 s: обе величины не превышают 0.020 s.

Между fetch и интеграцией показать рабочий каталог и полученный файл через show. Попросить указать местонахождение origin/main и сравнить его роль с серверной main в соседнем bare-репозитории.

Включение проверки

Почему для перехода main к U подходит fast-forward? N является предком U:

git merge --ff-only origin/main
git status --short

Main продвигается к U, CHECKS.md появляется в рабочем дереве. Нового коммита слияния эта операция не создаёт.

Содержимое CHECKS.md в PowerShell:

Get-Content -LiteralPath CHECKS.md

В fish: cat CHECKS.md.

Проверить обе записи и перевод миллисекунд в секунды. Попросить сопоставить количество коммитов до и после ff-only. При вопросе о расходящихся линиях восстановить общий предок и два родителя из знакомого слияния M.

Предложенная инструкция

Какую ошибку сравнения предотвращает дополнение README?

Прочитайте входной guide.patch. PowerShell:

Get-Content -LiteralPath ../incoming/guide.patch

Fish:

cat ../incoming/guide.patch

Патч добавляет в README.md строку:

Перед сравнением с порогом переведите миллисекунды в секунды.

Он подготовлен по README из N; U этот файл сохранил.

Попросить найти пути старой и новой стороны, строки контекста и добавление. Связать инструкцию с фактическими единицами проекта. Проверить, что патч не затрагивает исходные измерения.

Применимость патча

Как установить, что текущий текст подходит для применения?

git apply --stat ../incoming/guide.patch
git apply --check ../incoming/guide.patch
git status --short

Check проверяет применение без изменения файлов. Его успех показывает, что исходный текст подходит. После проверки status остаётся пустым.

Предметная проверка устанавливает, что новое указание правильно связывает measurements.tsv в ms и criteria.txt в s.

Попросить разделить два вопроса: подходит ли текст и верно ли указание. Предложить ошибочное дополнение о переводе в минуты: техническая применимость могла бы сохраниться, а смысл сравнения изменился бы.

Сохранение патча

Какой родитель будет у коммита с принятым дополнением?

git apply ../incoming/guide.patch
git --no-pager diff -- README.md
git add -- README.md
git commit -m "Уточнить сравнение единиц"

Новый P имеет родителя U:

main ──> P ──> U ──> N <── start

Обычный apply менял рабочий файл; commit сохранил подготовленный результат.

Прочитать родителя P и сравнить с состоянием до apply. Спросить, как пришлось бы выбрать ветку, если бы требовался родитель N. Уточнить различие совпадающего текста и требуемого происхождения.

Описание выпуска

Какие выполненные изменения нужно сообщить получателю версии 1.0?

Создайте VERSION со строкой 1.0. PowerShell 7:

Set-Content -LiteralPath VERSION -Value '1.0'

Fish:

printf '%s\n' '1.0' > VERSION

В редакторе создайте CHANGELOG.md:

# 1.0

- Проверены оба измерения по порогу 0.020 s.
- Указан перевод единиц перед сравнением.

Попросить связать каждую строку описания с конкретным сохранённым изменением. Проверить номер в VERSION и заголовке CHANGELOG. Перед фиксацией прочитать подготовленное содержимое обоих файлов.

Пометка коммита

Как сохранить имя проверенной версии при дальнейшем продвижении main?

git add -- VERSION CHANGELOG.md
git --no-pager diff --staged
git commit -m "Подготовить выпуск измерений 1.0"
git tag -a v1.0 -m "Измерения с проверкой порога"
git --no-pager show --no-patch v1.0

Итоговый R продолжает P. Объект аннотированного тега хранит ID помеченного коммита, автора тега, дату и сообщение. Имя v1.0 обращается к этому объекту и сохраняет выбранный R при дальнейших коммитах main.

Прочитать show: сначала сведения тега, затем коммита. Попросить объяснить, какая ссылка двинется после следующего commit в main. Сопоставить сохранённый R с рабочими файлами выпуска.

Проверка у получателя

Какие ссылки подтвердят, что shared.git хранит нужную версию выпуска?

git push origin main
git push origin v1.0
git rev-parse HEAD
git rev-parse 'v1.0^{commit}'
git ls-remote origin

У shared.git main теперь выбирает R. Для тега сравниваются объект тега и раскрытый коммит refs/tags/v1.0^{}. Раскрытый ID совпадает с R. Исходная серверная U сохранена как предок R.

Показать обе строки v1.0 из ls-remote. Попросить указать, какая из них сравнивается с HEAD. Затем найти U по родителям из R. Объяснить отдельную передачу тега и ветки.

Разность выпуска

Какая исходная версия нужна получателю для применения release.patch?

git diff --output=../release.patch start v1.0

Патч переводит файлы start/N в снимок R. Проверьте затронутые пути: README.md, CHECKS.md, VERSION и CHANGELOG.md.

Исходные criteria.txt и measurements.tsv сохранились. Проверка на отдельном чистом start должна дать весь снимок v1.0. Способ сравнения учитывает также добавленные файлы.

Прочитать созданную разность. Попросить назвать два исходных файла, которые в ней отсутствуют, и объяснить причину. Обсудить необходимую базу проверки до открытия временного каталога.

Архив выпуска

Как получить файлы выбранного коммита для передачи получателю?

git archive -o ../latency-1.0.zip --prefix=latency-1.0/ v1.0

Откройте ZIP и проверьте шесть файлов под latency-1.0/: README.md, criteria.txt, measurements.tsv, CHECKS.md, VERSION, CHANGELOG.md. Содержимое берётся из R. Рабочая незакоммиченная правка в снимок не попадёт.

История .git в архив выпуска не входит. Для передачи истории сохраняют полный репозиторий.

Прочитать VERSION и criteria.txt непосредственно из извлечённого архива. Попросить выбрать подходящий материал для вопроса о родителях M и для вопроса о файлах версии 1.0.

Самостоятельный выпуск

В добровольном проекте отчёт развивается по расходящимся линиям M и F. Патч требуется сохранить коммитом с родителем A. Выпуск объединяет назначения обоих изменений и отдельное предложение инструкции.

Какие назначения двух изменений должен сохранить итоговый отчёт? Какая исходная версия нужна для отдельного патча? Порядок слияний и состав результата выбираются по условию.

Открыть самостоятельное условие и попросить найти его исходную базу. Сопоставить требуемого родителя P с родителем демонстрационного P. Попросить сформулировать назначения двух расходящихся изменений перед выбором порядка действий.
