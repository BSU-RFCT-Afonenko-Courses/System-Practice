6  Ветвление истории

Темы главы: родительские связи; ветка; HEAD; создание линии разработки; переключение; fast-forward; общий предок; коммит слияния; конфликт; проверка результата интеграции.

6.1 Родители коммита

В проекте latency-demo уже сохранены исходный порог 10 ms в A и уточнение до 12 ms в B. Рабочий эксперимент был отменён восстановлением из индекса; рабочее дерево и индекс совпадают с B. Это итог подготовки снимка.

HEAD ──> main ──> B ──> A

B: 12 ms; родитель B — A

Стрелка между коммитами идёт от потомка к его родителю — коммиту, который записан непосредственным предшественником. Предок достижим последовательным переходом по родителям. Например, в цепочке C → B → A коммит B — непосредственный родитель C; коммит A — предок C.

Связи родителей входят в данные коммита. Имена веток хранятся отдельно и могут перемещаться к новым коммитам. Для чтения истории:

git --no-pager log --graph --oneline --decorate --all

--graph рисует соединения, --all начинает обход от всех ссылок, --decorate подписывает текущие имена. Соседние строки вывода могут располагаться по-разному; родительство устанавливается по соединениям. [1, сс. 66–82]

6.2 Создание ветки

Описание проекта дополнится сведениями о происхождении данных. Создайте для этого отдельную линию с именем source-note:

git branch source-note
git branch --list
HEAD ──> main ────────┐
                     v
                     B ──> A
                     ^
         source-note ┘

branch source-note создаёт ещё одну ссылку на B. Содержимое файлов и текущая ветка сохраняются. Выберите новую ветку:

git switch source-note

HEAD указывает на source-note. Обе ветки пока выбирают B, поэтому файлы сохранили прежнее содержимое. Добавьте в конец README.md отдельную строку:

Источник: учебные измерения двух датчиков.
git add -- README.md
git --no-pager diff --staged
git commit -m "Указать происхождение измерений"
HEAD ──> source-note ──> C ──> B ──> A
                             ^
                      main ──┘

C содержит дополненное описание и прежние criteria.txt/measurements.tsv. Его родитель — B. Продвинулась текущая ветка source-note; main продолжает выбирать B.

6.3 Переключение снимка

git switch main

HEAD снова указывает на main. При чистом рабочем состоянии Git обновляет индекс и файлы по выбранному снимку B. Строка происхождения исчезнет из рабочего README.md; она сохранена в C, доступном через source-note. Порог в обоих снимках равен 12 ms.

HEAD ──> main ──> B ──> A
                 ^
source-note ──> C┘

Совместимые незакоммиченные изменения могут переходить при переключении вместе с рабочим деревом. Когда переключение затёрло бы их, Git отказывается выполнять действие. Перед сменой линии проверяйте status и сохраняйте законченные изменения. Руководство switch.

6.4 Продвижение fast-forward

Описание из source-note готово к включению в основную линию:

git merge --ff-only source-note

Вершина main/B является предком C. Для включения C достаточно переместить main к уже существующему коммиту. Такое продвижение называется fast-forward.

HEAD ──> main ────────┐
                     v
                     C ──> B ──> A
                     ^
         source-note ┘

Нового коммита эта операция не создала. Индекс и рабочие файлы обновились до C; строка происхождения снова присутствует в README.md. Для fast-forward подходит и более длинный путь по родителям: исходная вершина должна быть предком новой.

--ff-only допускает продвижение по существующей истории. Если указанная линия уже целиком включена в текущую историю, Git сообщит Already up to date. При расхождении линий этот режим завершится отказом, сохранив их вершины. Руководство merge.

6.5 Расхождение линий

Два требования к критерию отчёта появились независимо:

  • порог нужно увеличить с 12 до 20 ms;
  • порог в документе нужно выражать в секундах.

Создайте ветку второго изменения от C:

git switch -c seconds

switch -c создаёт ветку от текущего коммита и сразу выбирает её. Замените строку criteria.txt на latency_limit = 0.012 s. В README.md добавьте строку Порог в criteria.txt выражен в секундах. Значения measurements.tsv продолжают выражаться в миллисекундах.

git add -- criteria.txt README.md
git --no-pager diff --staged
git commit -m "Выразить порог в секундах"
git switch main

Коммит S создан в seconds. После возврата к main/C рабочий критерий снова равен 12 ms, а добавленная в S строка README.md отсутствует. Измените критерий на latency_limit = 20 ms и сохраните основное изменение:

git add -- criteria.txt
git commit -m "Повысить порог до 20 ms"
HEAD ──> main ──> T ──┐
                     v
                     C ──> B ──> A
                     ^
       seconds ──> S ┘

C: 12 ms     T: 20 ms     S: 0.012 s

T и S имеют общего родителя C. Из T нельзя перейти по родителям к S, из S — к T. Для соединения линий требуется новый результат, содержащий решение для обоих изменений.

6.6 Трёхстороннее слияние

Слияние использует общее исходное состояние и изменения каждой из двух линий. В этом опыте сравниваются C, T и S. Изменение README.md есть только на стороне S, поэтому оно может войти в результат автоматически. Строка criteria.txt изменена на обеих сторонах.

Находясь в main/T с чистым рабочим деревом, выполните:

git merge seconds
git status

Git остановит слияние на конфликте criteria.txt. Конфликт слияния означает, что автоматическое соединение изменений требует решения человека. В рабочем файле появятся варианты:

<<<<<<< HEAD
latency_limit = 20 ms
=======
latency_limit = 0.012 s
>>>>>>> seconds

Первая часть принадлежит текущей линии main, вторая — присоединяемой seconds. До разрешения HEAD и main остаются на T. Ссылка MERGE_HEAD указывает на S, который присоединяется. Для конфликтного файла индекс хранит исходную версию и версии обеих сторон; подготовить обычный снимок этого файла предстоит после выбора результата. Представление конфликта.

6.7 Разрешение конфликта

Новый порог — 20 ms, а выбранная единица записи — секунда. Поскольку 1000 ms = 1 s, совместное выполнение требований даёт 0.020 s. Замените весь конфликтный блок одной строкой:

latency_limit = 0.020 s

Простое сохранение первой стороны потеряло бы новую единицу; сохранение второй оставило бы прежнюю величину порога. Решение получается из назначения изменений и соотношения единиц. Удаление маркеров завершается проверкой значения, единицы и согласованного описания в README.md.

git add -- criteria.txt
git --no-pager diff --staged
git commit -m "Согласовать порог"
git status --short

add отмечает выбранное содержимое конфликтного файла как подготовленное. При незавершённом слиянии commit сохраняет также второго родителя. Вместо последнего commit можно вызвать git merge --continue и ввести сообщение в редакторе.

HEAD ──> main ──> M ──> T ──┐
                 │         v
                 │         C ──> B ──> A
                 v         ^
     seconds ──> S ────────┘

M: 0.020 s; родители M — T и S

main переместилась на M, seconds осталась на S. Оба исходных изменения достижимы из M по родительским связям. В README.md сохранена строка о секундах; измерения по-прежнему имеют свою указанную единицу ms. Рабочее дерево и индекс совпадают со снимком M.

6.8 Проверка интеграции

git --no-pager log --graph --oneline --decorate --all
git --no-pager show --no-patch --format=raw HEAD
git show 'HEAD:criteria.txt'
git status

У show --format=raw поля parent называют непосредственных родителей коммита. В M их два: T и S. Отдельно проверяется содержимое снимка: наличие родительских связей сохраняет происхождение, а выбранные файлы устанавливают результат разрешения.

При необходимости отказаться от незавершённого слияния служит git merge --abort. В описанном опыте слияние начиналось с чистого состояния, поэтому можно восстановить его исходные файлы и индекс. Незакоммиченные правки, существовавшие до merge и продолженные во время него, осложняют восстановление; законченные изменения сохраняют до начала интеграции. Руководство merge.

После интеграции историю можно передать в другой репозиторий. Для этого используются удалённые адреса и операции обмена.
