5  Состояние репозитория

Темы главы: сохранение версий; организация истории; система Git; репозиторий; снимок проекта; коммит; рабочее дерево; индекс; подготовка изменения; чтение истории; восстановление файла.

5.1 Сохранение версий

После изменения проекта может понадобиться прежняя версия: сравнить результаты, вернуть удачное решение или выяснить причину ошибки. Знакомый способ сохранения — скопировать папку перед работой:

latency-original/     порог 10 ms
latency-corrected/    порог 12 ms
latency-experiment/   порог 20 ms

Каждая копия содержит файлы своего состояния. По именам папок трудно установить, какие изменения связывают состояния, кто их внёс и какую версию использовали при получении результата. Для совместной работы потребуется ещё сопоставлять изменения из разных копий.

Система управления версиями сохраняет состояния файлов и сведения об их изменениях. История позволяет обратиться к выбранной версии, сравнить её с другой и связать результат с внесённым изменением.

5.2 Организация истории

Репозиторий хранит версии файлов и сведения для обращения к ним. В локальной системе управления версиями он находится на одном компьютере. Программа сохраняет версии в этой базе и позволяет выбирать их для чтения и сравнения. Такой способ организует личную историю работы на данном компьютере; общего сервера для участников нет.

В централизованной системе общая история хранится на сервере. Участники получают рабочие файлы и редактируют их на своих компьютерах. Для сохранения новой версии в общей истории требуется соединение с сервером. Он сосредоточивает хранение истории и управление доступом участников. При недоступности сервера локальные файлы можно продолжать редактировать; новые версии попадут в общую историю после восстановления соединения.

В распределённой системе обычная полная копия проекта содержит собственный репозиторий с историей. Сохранение версий, чтение истории и сравнение состояний выполняются локально. Участники могут независимо подготавливать изменения, затем передавать их друг другу. Общий сервер может служить выбранным местом обмена; для локального сохранения версии обращение к нему не требуется. Такой способ поддерживает самостоятельное развитие нескольких копий до очередного обмена.

Git — распределённая система управления версиями. Его локальный репозиторий позволяет вести историю проекта без соединения с сервером; обмен передаёт данные истории между репозиториями. [1, сс. 10–18]

5.3 Возникновение Git

Git возник в 2005 году при разработке ядра Linux. До этого проект использовал BitKeeper. Linus Torvalds связывал полезность распределённой работы с возможностью разработчика вести собственный репозиторий и предлагать подготовленные изменения. После прекращения прежнего сотрудничества с BitKeeper потребовалось сохранить такой способ работы. Для Linux были существенны частые слияния большого числа изменений, быстрые операции и целостность данных истории. Интервью Torvalds.

В первоначальном README Git уже описаны объекты содержимого, деревья файлов и записи со связями предшествования. Связи между сохранёнными состояниями позволяют объединять линии разработки, у которых есть общее начало.

5.4 Снимок проекта

Репозиторий Git хранит объекты содержимого, сохранённые состояния и ссылки для обращения к ним. У обычного локального репозитория служебные данные находятся в каталоге .git внутри папки проекта. Рабочее дерево содержит файлы, которые открывает редактор и читают программы. В нём продолжается текущая работа.

Снимок задаёт содержимое всех отслеживаемых файлов проекта в выбранном состоянии. Коммит связывает такой снимок с сообщением, сведениями об авторе и родительскими коммитами. Начальный коммит имеет ноль родителей; обычное продолжение истории — одного. Для коммита слияния существенны связи с несколькими предшествующими линиями.

коммит B ──> снимок файлов B
    │         criteria.txt: latency_limit = 12 ms
    │         README.md: описание проекта
    │         measurements.tsv: исходные измерения
    v
родитель A ─> снимок файлов A
              criteria.txt: latency_limit = 10 ms
              README.md: то же описание
              measurements.tsv: те же измерения

Изменение порога видно при сравнении снимков A и B. Неизменившиеся файлы тоже входят в оба состояния проекта; Git может повторно использовать объекты их содержимого. Коммит хранит ссылки на снимок и родителей. Различие файлов вычисляется при сравнении выбранных состояний. [1, сс. 15–18, 66–68]

Идентификатор коммита вычисляется из его данных. В выводе Git часто показывается короткое однозначное начало идентификатора. Данные автора, время, сообщение и родители участвуют в данных коммита, поэтому одинаковые файлы у разных студентов могут иметь разные идентификаторы истории. Буквы A и B в схемах обозначают коммиты текущего опыта.

Ветка — именованная изменяемая ссылка на коммит. В обычной работе HEAD указывает на текущую ветку; через неё определяется текущий коммит. После обычного commit текущая ветка перемещается к новому коммиту. Начальную ветку опыта назовём main.

5.5 Создание локальной истории

Проект latency-demo хранит измерения задержки и критерий включения измерения в отчёт. Исходные файлы:

Файл Содержимое
criteria.txt latency_limit = 10 ms
measurements.tsv Столбцы sensor, latency_ms; записи north, 8 и south, 18; разделитель TAB
README.md Назначение двух файлов; единица исходных измерений — миллисекунда

Получить файлы можно из демонстрационного архива. В нём обычный каталог без .git. Перейдите в распакованный latency-demo в PowerShell 7 или fish. Команды Git одинаковы в обеих оболочках.

git --version
git init -b main
git status

init создаёт репозиторий в текущей папке. Ветка main ещё не содержит коммита: её первый снимок предстоит сохранить. Файлы пока неотслеживаемые — Git видит их в рабочем дереве, но они ещё не включены в подготовленный снимок. Руководство init.

Автор коммита задаётся именем и почтой. Команды без --global сохраняют настройку только этого репозитория. Подставьте своё имя и выбранную почту:

git config user.name "Ваше имя"
git config user.email "YOUR_EMAIL"
git config --get user.name
git config --get user.email

Эти значения попадут в будущие коммиты. GitHub связывает автора с аккаунтом по добавленной в аккаунт почте. Свой noreply из настроек GitHub позволяет скрыть личную почту в новых коммитах. Аутентификация и право отправки изменений проверяются при подключении к серверу. Настройка почты коммитов.

Индекс хранит содержимое, подготовленное для следующего снимка. Команда add переносит в него выбранные версии файлов из рабочего дерева. Обычный commit сохраняет подготовленный снимок:

git add -- README.md criteria.txt measurements.tsv
git --no-pager diff --staged
git commit -m "Сохранить исходные измерения"
git status --short

-- отделяет пути от параметров. diff --staged перед первым коммитом показывает всё подготовленное содержимое. --no-pager выводит результат непосредственно в терминал. Сообщение commit описывает сохранённое изменение. Пустой короткий статус после этих действий означает, что рабочие файлы и индекс совпадают с новым снимком и неотслеживаемых файлов нет.

HEAD ──> main ──> A

A: criteria.txt = 10 ms
индекс: 10 ms; рабочий файл: 10 ms

5.6 Подготовка снимка

Измените порог на 12 ms. В PowerShell 7 строку записывает Set-Content:

Set-Content -LiteralPath criteria.txt -Value 'latency_limit = 12 ms'

В fish такую же строку с завершающим переводом строки записывает printf:

printf '%s\n' 'latency_limit = 12 ms' > criteria.txt

Подготовьте этот файл для следующего снимка:

git add -- criteria.txt

После add измените рабочий порог на 20 ms. В PowerShell:

Set-Content -LiteralPath criteria.txt -Value 'latency_limit = 20 ms'

В fish:

printf '%s\n' 'latency_limit = 20 ms' > criteria.txt
Место Порог Как возникло состояние
HEAD, коммит A 10 ms Первый сохранённый снимок
Индекс 12 ms Содержимое в момент git add
Рабочее дерево 20 ms Последующая правка файла

add сохраняет содержимое на момент выполнения. Последующее редактирование меняет рабочий файл; подготовленное значение остаётся 12. Повторный add этого файла подготовил бы уже 20. Руководство add.

5.7 Сравнение состояний

git status --short
git --no-pager diff -- criteria.txt
git --no-pager diff --staged -- criteria.txt

Короткий статус содержит MM criteria.txt. Для обычного изменённого файла первая колонка описывает индекс относительно HEAD, вторая — рабочий файл относительно индекса. Обе пары различаются.

Команда Сравнение Существенные строки результата
git diff Индекс → рабочее дерево -latency_limit = 12 ms, +latency_limit = 20 ms
git diff --staged HEAD → индекс -latency_limit = 10 ms, +latency_limit = 12 ms
git diff HEAD HEAD → рабочее дерево -latency_limit = 10 ms, +latency_limit = 20 ms

Знак - обозначает строку исходной стороны сравнения, + — строку новой стороны. ?? в коротком статусе обозначает неотслеживаемый файл. Для конфликтов Git использует отдельные сочетания статуса. status, diff.

Сохраните подготовленные 12:

git commit -m "Уточнить порог до 12 ms"
git status --short
HEAD ──> main ──> B ──> A
                 │     │
                 12 ms 10 ms

индекс: 12 ms; рабочий файл: 20 ms

Стрелка B → A означает, что A — родитель B. После commit main указывает на B, индекс совпадает с его снимком, а рабочий эксперимент с 20 сохраняется. Статус содержит M criteria.txt: подготовленных изменений нет, рабочее изменение осталось. Это действие относится к обычному git commit без -a и без путей; дополнительные режимы выбора содержимого описаны в руководстве commit.

5.8 Чтение истории

git --no-pager log --oneline --decorate
git --no-pager log -p -- criteria.txt
git show 'HEAD:criteria.txt'
git show ':criteria.txt'

log --oneline выводит идентификатор и первую строку сообщения каждого коммита. --decorate добавляет текущие имена ссылок. log -p показывает изменения выбранного файла. show 'HEAD:criteria.txt' читает его из текущего коммита, show ':criteria.txt' — из индекса.

Чтобы прочитать прежнее содержимое, возьмите идентификатор A из log и подставьте его перед двоеточием: git show 'ID_A:criteria.txt'. Имя ID_A в этой записи заменяется настоящим идентификатором. Чтение исторического файла оставляет рабочее дерево прежним. [1, сс. 42–48]

5.9 Восстановление файла

Для переноса сохранённого содержимого существенны источник и назначение. restore без параметров назначения меняет рабочее дерево; его обычный источник — индекс. В текущем опыте рабочее значение 20 можно заменить подготовленными 12:

git restore -- criteria.txt
git status --short

Теперь HEAD, индекс и рабочий файл содержат 12; статус пуст. Незакоммиченный эксперимент 20 был заменён. Перед восстановлением нужно прочитать соответствующий diff и сохранить полезные рабочие изменения.

Перенос Команда Что сохраняется
Индекс → рабочий файл git restore -- criteria.txt HEAD и индекс
HEAD → индекс git restore --staged -- criteria.txt Рабочий файл
Выбранный коммит → рабочий файл git restore --source=ID_A --worktree -- criteria.txt HEAD и индекс

У формы --staged источник по умолчанию — HEAD. Явный --source выбирает другой коммит. Историческое содержимое, перенесённое только в рабочий файл, можно проверить, подготовить через add и сохранить новым коммитом. Существующие коммиты при таком восстановлении сохраняются. Руководство restore.

У одного снимка могут появиться разные продолжения. Их именование и соединение раскрывает ветвление истории.
