8  Сопровождение проекта

Темы главы: проверка другой версии; связанные рабочие деревья; получение изменений; патч и выбор базы; аннотированный тег; снимок выпуска; двоичные файлы; Git LFS; условия параллельной разработки.

8.1 Версия для получателя

Сопровождение сохраняет пригодность проекта после очередного изменения. Поступившую работу связывают с её исходной версией, согласуют с текущими требованиями и проверяют перед передачей получателю. Для воспроизводимого выпуска нужны сохранённый снимок, сведения о его происхождении и способ получить именно эту версию.

В проекте измерений уже согласованы величина порога и единица его записи. После обмена репозиториями обе локальные main выбирают N. Этот коммит продолжает M, который сохранил две линии T и S с общей базой C. Порог в criteria.txt равен 0.020 s, measurements.tsv по-прежнему содержит north — 8 ms и south — 18 ms. README.md дополнен строкой проверки во второй копии.

main ──> N ──> M ──> T ──> C
               │           ^
               └──> S ─────┘

Ветка main продолжит двигаться при новых коммитах. Получателю выпуска нужно устойчивое имя проверенной версии. Архив с файлами этой версии позволит открыть проект без рабочего репозитория. Для следующего изменения сохраняется история, по которой можно установить родителей и исходные условия работы.

8.2 Подготовленная копия

Демонстрационный архив восстанавливает проект измерений в состоянии N и добавляет материалы для следующего выпуска. Распакуйте его в новую папку:

maintenancelab/
├── work/                 проект измерений и .git
├── shared.git/           репозиторий обмена
└── incoming/
    └── guide.patch       дополнение README.md

В work сохранены история до N и main/N. Легковесный тег start — имя со ссылкой непосредственно на N; новые коммиты ветки сохраняют этот тег на исходной версии. Рабочие файлы и индекс чисты. shared.git — bare-репозиторий: объекты и ссылки Git без рабочего дерева. Его main уже продолжена коммитом U с родителем N. U добавляет CHECKS.md с проверкой обоих исходных измерений по порогу 0.020 s. Остальные файлы сохранились. Соседний каталог доступен через файловую систему. [1, сс. 110–115]

Откройте терминал в maintenancelab/work. Команды Git подходят для PowerShell 7/Windows и fish/Linux; используется одна выбранная среда. Задайте собственные имя и почту автора в этом репозитории:

git config user.name "Ваше имя"
git config user.email "YOUR_EMAIL"
git status --short
git --no-pager log --graph --oneline --decorate --all

8.3 Проверка другой версии

Для сравнения README из M и N можно развернуть M рядом с текущей работой. Связанное рабочее дерево Git имеет собственные файлы, индекс и HEAD, используя общую базу объектов и обычные ссылки основного репозитория.

git worktree add --detach ../previous HEAD~1
git worktree list
git -C ../previous show 'HEAD:README.md'
git show 'HEAD:README.md'

HEAD~1 выбирает первого родителя текущего N, то есть M. Параметр --detach помещает HEAD дополнительного дерева непосредственно на M. Новая ветка для чтения старой версии не создаётся. Параметр -C выполняет команду Git в названном каталоге. В основном work остаются main/N и его файлы; в previous отсутствует строка проверки второй копии.

work:     HEAD ──> main ──> N    свой индекс, файлы N
previous: HEAD ───────────> M    свой индекс, файлы M
                    общие объекты и обычные refs

После просмотра проверьте чистоту дополнительного дерева и удалите его через Git:

git -C ../previous status --short
git worktree remove ../previous

Обычный remove отказывается удалять дерево с изменёнными файлами. Внутри связанного каталога .git является файлом со ссылкой на служебные данные. Для переноса всей истории нужно сохранить общее хранилище; копирование одного такого каталога оставит внешнюю зависимость. Руководство worktree.

8.4 Получение проверки

В основном work задайте адрес подготовленного bare-репозитория:

git remote add origin ../shared.git
git fetch origin
git --no-pager log --graph --oneline --decorate --all
git show 'origin/main:CHECKS.md'

Fetch получает U и обновляет локальную origin/main. Собственная main и рабочие файлы ещё соответствуют N. В полученной проверке указано: 8 ms = 0.008 s и 18 ms = 0.018 s; обе величины не превышают 0.020 s. Поскольку N является предком U, готовую проверку можно включить продвижением ветки:

git merge --ff-only origin/main

Теперь main и файлы соответствуют U. Если полученная и собственная линии расходятся, требуется их интеграция с сохранением требований обеих сторон. При конфликте исходные версии читают отдельно, выбирают согласованный результат и завершают слияние, как в разборе порога.

8.5 Изменение в патче

Патч описывает изменение файлов относительно исходного содержимого. В нём указаны пути, участки контекста, удаляемые и добавляемые строки. Входной guide.patch подготовлен по README из N:

diff --git a/README.md b/README.md
--- a/README.md
+++ b/README.md
@@ -5,3 +5,4 @@
 Источник: учебные измерения двух датчиков.
 Порог в criteria.txt выражен в секундах.
 Проверка: данные прочитаны во второй копии.
+Перед сравнением с порогом переведите миллисекунды в секунды.

a/ и b/ обозначают старую и новую стороны. В строке @@ записаны начало и длина участка каждой стороны. Пробел перед строкой обозначает сохраняемый контекст, + — добавление, - — удаление. Формат патча.

Прочитайте файл целиком. В PowerShell:

Get-Content -LiteralPath ../incoming/guide.patch

В fish:

cat ../incoming/guide.patch

Проверьте его действие и применимость:

git apply --stat ../incoming/guide.patch
git apply --check ../incoming/guide.patch

--stat показывает затронутые файлы и объём правки. --check проверяет возможность применения без записи. U добавил другой файл, сохранив README из N, поэтому исходный контекст патча подходит. При отказе проверки нужно сопоставить путь, кодировку и исходный текст с выбранной версией. Успешная проверка устанавливает применимость; смысл дополнения проверяется по единицам исходных данных и порога. [1, сс. 160–165]

git apply ../incoming/guide.patch
git --no-pager diff -- README.md
git add -- README.md
git commit -m "Уточнить сравнение единиц"

Обычный apply изменяет рабочие файлы. Отдельные add и commit сохраняют результат в истории: новый P имеет родителя U. Исходный текст README в N и U совпадал, однако выбранный родитель P определяется текущей веткой в момент commit. Текстовый патч сам по себе не задаёт эту родительскую связь. Руководство apply.

Если изменение должно составить отдельную линию от заданной версии, сначала создают ветку от этой версии, затем проверяют и фиксируют патч. При последующем слиянии история сохраняет обе линии. Формат format-patch вместе с am позволяет передавать также сведения автора и сообщения коммитов; обычный diff-патч в этом опыте переносит файловое изменение. format-patch, am.

8.6 Именование выпуска

Выпуск — выбранная проверенная версия с именем и материалами для получателя. Для версии 1.0 создайте VERSION с единственной строкой 1.0. В PowerShell 7:

Set-Content -LiteralPath VERSION -Value '1.0'

В fish:

printf '%s\n' '1.0' > VERSION

В редакторе создайте CHANGELOG.md:

# 1.0

- Проверены оба измерения по порогу 0.020 s.
- Указан перевод единиц перед сравнением.

Сохраните выпуск и пометьте полученный коммит R:

git add -- VERSION CHANGELOG.md
git --no-pager diff --staged
git commit -m "Подготовить выпуск измерений 1.0"
git tag -a v1.0 -m "Измерения с проверкой порога"
git --no-pager show --no-patch v1.0

Аннотированный тег — отдельный объект с указанием помеченного объекта, автора тега, даты и сообщения. Имя v1.0 обращается к этому объекту. Ветка main перемещается при последующих коммитах; тег сохраняет выбранный R. У опубликованного имени версии сохраняют прежнее значение, чтобы получатели могли согласованно обращаться к выпуску. [1, сс. 58–63, 172–175], [4]

8.7 Передача выпуска

git push origin main
git push origin v1.0
git rev-parse 'v1.0^{commit}'
git ls-remote origin

R продолжает U через P; отправка main сохраняет прежнюю линию репозитория shared.git. Тег передаётся отдельной командой. Для аннотированного тега ls-remote показывает объект тега и строку с окончанием ^{} — помеченный коммит. Его ID должен совпасть с R и с новой main другого репозитория. [2], [3]

8.8 Снимок выпуска

Получатель может получить полный набор файлов R либо разность от своего исходного снимка start/N:

git diff --output=../release.patch start v1.0
git archive --format=zip --prefix=latency-1.0/ --output=../latency-1.0.zip v1.0

Первый аргумент diff задаёт исходную сторону, второй — итоговую. --output записывает патч средствами Git. Патч нужно проверить на чистой версии start; результат применения должен совпасть с файлами v1.0. Руководство diff.

Archive читает дерево выбранного коммита. В ZIP под latency-1.0/ попадают README.md, criteria.txt, measurements.tsv, CHECKS.md, VERSION и CHANGELOG.md из R. Незакоммиченные изменения рабочего дерева в этот набор не входят. Атрибут export-ignore, если он задан в проекте, исключает отмеченные пути из архива; в этом опыте таких исключений нет. Руководство archive.

Передаваемый материал Что может проверить получатель
Патч start → v1.0 Применимость к исходным файлам и получившийся снимок
Архив latency-1.0.zip Пути и содержимое файлов выпуска
Полный репозиторий Коммиты, родительские связи, ветки и теги

Архив выпуска содержит файлы выбранного дерева. Для чтения истории потребуется репозиторий с объектами и ссылками. Способы проверки патча и полной упаковки приведены в справочнике сопровождения.

8.9 Двоичное содержимое

Git сохраняет содержимое файлов как последовательности байтов. Для исходного текста построчный diff показывает изменённые выражения, а трёхстороннее слияние сопоставляет строки общей базы и двух продолжений. Формат изображения, архива или другого двоичного документа может требовать собственного способа сравнения и согласования. Например, две правки разных объектов рисунка нуждаются в программе, которая понимает эти объекты.

Встроенный драйвер binary при конфликте сохраняет текущую сторону в рабочем файле и оставляет путь неразрешённым. Проект может назначить специализированный драйвер слияния через атрибуты. Драйверы слияния. Само сохранение двоичного файла в истории не обеспечивает такого сравнения.

Большие меняющиеся файлы увеличивают объём хранимой истории и передачи обычной полной копии. Правила сервиса размещения задают дополнительные ограничения размера и квоты. GitHub описывает их отдельно и предлагает прикреплять распространяемые двоичные материалы к выпуску. Большие файлы GitHub (проверено 20.10.2026).

8.10 Git LFS

Git LFS хранит в Git небольшой текстовый указатель, а содержимое большого файла передаёт через отдельное хранилище. Указатель содержит версию формата, идентификатор SHA-256 содержимого и размер. Клиент LFS получает соответствующий объект для рабочего файла. Без него участник может увидеть только текст указателя. Устройство LFS, совместная работа.

Доступность объекта, квоты сервиса и включение LFS-содержимого в создаваемый GitHub архив проверяются по настройкам проекта. Для согласования двух версий изображения по-прежнему нужен способ, учитывающий его формат.

8.11 Параллельная работа

Если две задачи редактируют один рабочий каталог, они видят изменения друг друга и подготавливают общий индекс. Разные ветки предоставляют разные имена истории; для одновременных рабочих файлов каждой задаче нужен собственный каталог. Worktree позволяет получить такой каталог без второй полной базы объектов:

git worktree add -b docs-check ../docs-check main
git worktree list

Новая ветка docs-check начинается от текущей main, отдельный HEAD выбирает её в docs-check. Обычные ветки доступны всем связанным деревьям; по умолчанию Git запрещает одновременно выбрать одну ветку в двух деревьях. Настройка репозитория также обычно общая. Порты, базы данных и внешние сервисы могут оставаться общими и требуют самостоятельного разделения. Git worktree.

Руководство VS Code от 14.10.2026 предлагает для двух независимых агентных заданий разные worktree от общей базы, раздельную проверку изменений, затем проверку их объединения. Механизм Git сохраняет происхождение обеих работ; согласованность совместного результата устанавливают проверки проекта. Параллельные задачи VS Code.

8.12 Нагрузка большого проекта

Стоимость работы с репозиторием зависит от объёма истории, размера рабочих файлов, частоты записи и числа одновременных чтений. Частые проверки CI — автоматической сборки и испытаний — могут многократно запрашивать один снимок. Обновления одной общей ветки должны согласовывать её новое значение, даже когда изменения готовятся независимо.

В статье Anthropic от 13.10.2026, обновлённой 15.10, описан собственный огромный монорепозиторий — единое хранилище многих частей разработки. Основную нагрузку создавали постоянно подключённые задания и агенты. В Scion операции истории перенесены на сервер; клиент получает нужное содержимое по запросу и хранит ограниченный кэш. Такое устройство требует доступного сервера и собственного набора средств проверки, поиска и CI. Авторы связывают применимость решения с этим необычным масштабом. Источник Anthropic.

GitHub 06.10.2026, с обновлением 07.10, описал перестройку серверного хранения для множества конкурирующих записей и чтений. В прежней схеме новая долговечная реплика для чтения добавляла работу при каждой записи. Проектируемое устройство отделяет постоянное хранение Azure Blob Storage от вычислительных узлов с кэшами, сохраняя семантику Git. Это продолжаемая перестройка хостинга. Источник GitHub.
