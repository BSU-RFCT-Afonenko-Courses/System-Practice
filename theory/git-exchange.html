7  Обмен репозиториями

Темы главы: локальная копия; удалённый репозиторий; remote; отслеживаемая удалённая ветка; push; clone; fetch; интеграция полученной истории; интерфейсы Git; хостинг; протоколы; учётная запись; аутентификация SSH.

7.1 Копии истории

После слияния в проекте latency-demo основная ветка указывает на M. В его истории доступны оба родителя и исходные снимки. Чтобы получить тот же проект на другом компьютере, можно разместить репозиторий на сервере, а затем получить из него новую локальную копию. Каждая обычная копия имеет собственные рабочие файлы, индекс и ссылки.

первая локальная копия       репозиторий GitHub       вторая локальная копия
main ──> M                  main ──> M              main ──> M
своя история                переданная история      полученная история
свой индекс                                         свой индекс
свои рабочие файлы                                   свои рабочие файлы

Одинаковые идентификаторы называют одни и те же переданные коммиты. Новый локальный commit добавляет состояние только в свою копию. Для передачи этого состояния другой стороне требуется операция обмена. [1, сс. 54–58, 89–99]

7.2 Адрес удалённого репозитория

Remote — локальная настройка именованного другого репозитория: его адреса и правил обмена. Имя origin принято для исходного репозитория при клонировании. Можно использовать несколько remote с разными именами.

После создания пустого учебного репозитория GitHub его SSH-адрес имеет вид:

git@github.com:OWNER/REPOSITORY.git

git — служебное имя пользователя SSH у GitHub, github.com — сервер, OWNER/REPOSITORY.git — путь нужного репозитория. Аккаунт пользователя GitHub определяется предъявленным ключом. OWNER может называть владельца репозитория, к которому этому аккаунту предоставлен доступ.

В настройках первой локальной копии этот адрес получает имя:

git remote add origin git@github.com:OWNER/REPOSITORY.git
git remote -v

Подставляются реальные owner и имя созданного репозитория. remote add сохраняет настройку локально; передачи коммитов при этом ещё нет. remote -v показывает адреса получения и отправки. Адреса репозиториев GitHub.

Отслеживаемая удалённая ветка origin/main — локальная ссылка, хранящая полученное при обмене состояние main другого репозитория. Она обновляется при соответствующих операциях обмена.

7.3 Клиенты Git

Команды git add, commit, switch и push доступны через командный интерфейс Git. Графический клиент показывает изменения и историю в окнах. Интеграция IDE позволяет выполнять такие операции рядом с редактором исходников. Для понимания результата существенны выбранные файлы, содержимое индекса, текущая ветка и репозиторий назначения.

Например, кнопка подготовки файла в интерфейсе клиента меняет индекс, а сохранение файла в редакторе меняет рабочее дерево. После commit история локального репозитория уже содержит новую версию. Отправка на сервер выполняет отдельное действие push.

GitHub размещает репозитории на сервере и управляет доступом к ним через аккаунты. Веб-интерфейс служит созданию репозитория, просмотру истории и настройке доступа. GitHub CLI, команда gh, предоставляет командный интерфейс к возможностям GitHub.

7.4 Протоколы обмена

Способ обращения Пример адреса Свойства
Локальный путь ../shared-project Доступ к другому репозиторию через файловую систему; права задаёт ОС
HTTPS https://github.com/OWNER/REPOSITORY.git Защищённый сетевой канал; для записи GitHub требуется аутентификация
SSH git@github.com:OWNER/REPOSITORY.git Защищённый канал и аутентификация ключом в маршруте GitHub
Git protocol git://example.org/project.git Передача без встроенного шифрования и аутентификации

GitHub прекратил поддержку git:// 15 марта 2022 года. Изменение безопасности протоколов. Для HTTPS на личном компьютере Git Credential Manager может открыть вход через браузер и сохранить результат в системном хранилище учётных данных. Пароль аккаунта GitHub для Git-операций по HTTPS не принимается. Git for Windows поставляется с GCM. [1, сс. 110–115]

Видимость репозитория определяет, кому GitHub отдаёт его содержимое. Публичный репозиторий доступен для чтения всем; частный — пользователям с предоставленным доступом. Шифрование канала защищает передачу между клиентом и сервером. Файлы публичного репозитория после передачи остаются публично доступными независимо от выбранного защищённого протокола.

7.5 Учётная запись

Для размещения собственного проекта нужен личный аккаунт GitHub. Регистрация связывает имя аккаунта со способом входа и почтой. При существующем аккаунте используется он. Подтверждение почты завершает её проверку и открывает связанные возможности аккаунта.

В настройках Settings → Password and authentication настраивается защита входа. При настройке двухфакторной аутентификации приложение TOTP генерирует одноразовый код. Коды восстановления позволяют войти при утрате доступа к обычному второму фактору; их сохраняют в личном защищённом хранилище. В проект и отчёт эти сведения не помещаются. Настройка 2FA, восстановление доступа.

Имя и почта в локальных коммитах задаются отдельно через git config. Почта будет видна читателям истории. При выборе GitHub noreply нужно скопировать адрес из собственных настроек аккаунта. Этот адрес связывает коммиты с профилем и скрывает личную почту в новых коммитах. Почта автора.

7.6 Аутентификация SSH

SSH устанавливает защищённое соединение через сеть. При работе с GitHub нужно установить личность сервера, подтвердить свой аккаунт и получить разрешение на операцию с выбранным репозиторием.

Пара пользовательских ключей состоит из закрытого и открытого ключей. Закрытый ключ позволяет создать подпись; открытый — проверить её. Открытый ключ регистрируется в аккаунте GitHub. Клиент подписывает данные аутентификации, связанные с текущим сеансом; сервер проверяет подпись и соответствие ключа аккаунту. Закрытый ключ остаётся у клиента. RFC 4252, §7.

Парольная фраза защищает сохранённый закрытый ключ. Агент SSH предоставляет клиенту возможность выполнять подписи загруженным ключом. Это позволяет пользоваться ключом в последующих соединениях без повторного ввода парольной фразы для каждой операции. Доступность ключа зависит от выбранного агента и его состояния.

Пара ключей сервера принадлежит GitHub. Сервер создаёт подпись данных текущего обмена своим закрытым ключом. Клиент проверяет подпись открытым ключом сервера. Подпись подтверждает, что сторона текущего соединения владеет соответствующим закрытым ключом. RFC 4253, §8.

Принадлежность открытого ключа GitHub устанавливается отдельно. Отпечаток — компактное представление ключа для сверки по доверенному источнику. При первом запросе доверия пользователь сравнивает тип ключа и полный отпечаток с официальной страницей GitHub. Пользователь отвечает yes только после совпадения; при различии соединение прерывают и выясняют причину.

Клиент                                      GitHub
  │                            подпись данных обмена
  │                            закрытым ключом сервера
  │<── открытый ключ сервера + подпись ───────│
  │ доверие ключу, проверка подписи            │
  │<══════ защищённый сеанс установлен ══════>│
  │── пользовательский открытый ключ, подпись >│
  │                            проверка аккаунта
  │── запрос операции с OWNER/REPOSITORY ─────>│
  │                            проверка прав  │
  │<══════════ передача объектов Git ════════>│

Обмен также вырабатывает ключи сеанса. Они защищают конфиденциальность и целостность последующей передачи, включая пользовательскую аутентификацию, запрос операции и данные Git. RFC 4253, §§1, 7.

Запись доверенного сервера в known_hosts позволяет проверять его ключ при следующих подключениях. Изменение известного ключа вызывает диагностику и требует выяснения причины. Подпись Git-коммита связывает его данные с ключом подписанта и проверяется при чтении истории. Ключ доступа в данном маршруте добавляется с типом Authentication. Назначения ключей SSH.

7.7 Windows OpenSSH

Для Windows используется системный клиент OpenSSH и служба Windows ssh-agent. Git for Windows также может содержать собственный ssh, поэтому клиент Git явно связывается с системным экземпляром. GitHub: выбор агента на Windows.

В PowerShell 7 задайте пути программ и проверьте клиент:

$openSshDir = Join-Path $env:WINDIR 'System32/OpenSSH'
$sshClient = Join-Path $openSshDir 'ssh.exe'
$sshKeygen = Join-Path $openSshDir 'ssh-keygen.exe'
$sshAdd = Join-Path $openSshDir 'ssh-add.exe'
Test-Path -LiteralPath $sshClient
& $sshClient -V

Test-Path должен вернуть True, а последняя команда — версию OpenSSH. Оператор & запускает программу по пути в переменной. Если компонента нет, установите OpenSSH Client через дополнительные компоненты Windows по официальной инструкции. Установка системного компонента требует прав администратора.

В отдельном PowerShell с правами администратора разрешите ручной запуск службы агента и запустите её:

Get-Service -Name ssh-agent | Set-Service -StartupType Manual
Start-Service ssh-agent
Get-Service ssh-agent

Состояние должно быть Running. Тип Manual означает, что после остановки службы или перезагрузки её может потребоваться запустить снова. Для ключей и обычной работы вернитесь в PowerShell своего пользователя.

Проверьте действующую настройку клиента Git:

git config --global --get core.sshCommand

Если она уже задана, её значение показывает ранее выбранную команду. При переходе на системный Windows OpenSSH сохраните новое значение:

$sshProgram = '"' + $sshClient.Replace('\', '/') + '"'
git config --global core.sshCommand $sshProgram
git config --global --get core.sshCommand

Путь с прямыми косыми чертами и кавычками пригоден для вызова из Git. --global задаёт клиент для репозиториев текущего пользователя; локальные настройки отдельного репозитория могут его переопределить. Диагностика выбора клиента приведена в справочнике SSH.

7.8 Существующие ключи

Перед генерацией проверьте уже настроенные ключи и аккаунт, которому они принадлежат. В PowerShell:

Get-ChildItem -Force -LiteralPath "$HOME/.ssh"

В fish:

ls -la ~/.ssh

При отсутствии каталога команда сообщит об этом. Файлы вида id_ed25519 и id_ed25519.pub образуют обычную пару; расширение .pub обозначает открытый ключ. Существующая пригодная пара может использоваться повторно. Наличие ключей в другом выбранном ранее месте проверяется по своей настройке. Проверка ключей.

Для новой пары выберите свободное имя, например id_ed25519_course. Проверьте отсутствие обоих файлов с этим именем и с окончанием .pub. Если имя занято, выберите другое. В PowerShell 7:

New-Item -ItemType Directory -Force -Path "$HOME/.ssh"
$keyPath = Join-Path $HOME '.ssh/id_ed25519_course'
Test-Path -LiteralPath $keyPath
Test-Path -LiteralPath "$keyPath.pub"

Оба результата для нового имени должны быть False. Генерация:

& $sshKeygen -t ed25519 -C 'course-computer' -f $keyPath
& $sshAdd $keyPath

-t выбирает тип ключа, -C добавляет понятную подпись устройства, -f задаёт файл. При запросе введите парольную фразу и её подтверждение; при добавлении в агент она открывает ключ для использования. Эти команды выполняются обычным пользователем. Существующие файлы ключей сохраняются.

Для существующей пары задайте $keyPath равным её фактическому пути и выполните вызов ssh-add.exe с этим значением. Генерация новой пары в таком случае не требуется; открытый файл находится по пути $keyPath.pub.

7.9 Агент в fish/Linux

В Linux используется клиент OpenSSH. Проверьте его версию и доступность агента:

ssh -V
ssh-add -l

Последняя команда показывает отпечатки ключей агента либо сообщает, что ключей нет или агент недоступен. Доступный агент можно использовать. При отсутствии агента запустите отдельный сеанс fish под его управлением:

ssh-agent fish

Команды внутри этого сеанса получают адрес агента через окружение. После завершения вложенного fish командой exit запущенный для него агент завершится. Руководство ssh-agent.

Для новой пары подготовьте каталог и проверьте выбранное имя:

mkdir -p ~/.ssh
test -e ~/.ssh/id_ed25519_course
echo $status
test -e ~/.ssh/id_ed25519_course.pub
echo $status

Код 0 означает, что путь существует; при занятом имени нужно выбрать другое. После подтверждения свободного имени:

ssh-keygen -t ed25519 -C 'course-computer' -f ~/.ssh/id_ed25519_course
ssh-add ~/.ssh/id_ed25519_course

Если выбрана существующая пара, выполните только ssh-add с её путём. Ключи создаются и открываются самим пользователем на его компьютере.

7.10 Регистрация открытого ключа

Откройте Settings → SSH and GPG keys → New SSH key в GitHub. Укажите узнаваемое название компьютера и тип Authentication. В поле ключа вставляется полное содержимое выбранного файла .pub. Его можно прочитать в PowerShell:

Get-Content -Raw -LiteralPath "$keyPath.pub"

В fish:

cat ~/.ssh/id_ed25519_course.pub

Закрытый файл без .pub остаётся в личном каталоге ключей. После добавления открытого ключа аккаунт может принимать подтверждение соответствующим закрытым ключом. Добавление ключа в аккаунт.

7.11 Проверка соединения

В основном Windows-маршруте проверяется именно выбранный системный клиент:

& $sshClient -T git@github.com
$LASTEXITCODE

В fish:

ssh -T git@github.com
echo $status

-T отключает выделение псевдотерминала. При первом подключении клиент может показать ключ сервера и запросить доверие. Сверьте тип ключа и полный отпечаток с текущей официальной страницей GitHub. Подтверждение yes вводится после совпадения. При несовпадении соединение останавливают и проверяют адрес сервера и причину различия.

Признак успешной аутентификации:

Hi USERNAME! You've successfully authenticated, but GitHub does not provide shell access.

USERNAME должен быть вашим ожидаемым аккаунтом. GitHub предоставляет Git-операции и завершает этот тест без интерактивной оболочки; его штатный код завершения — 1. Код читают сразу после ssh. Сообщение Permission denied (publickey) требует проверки выбранного ключа, агента и регистрации ключа в аккаунте. Проверка SSH на GitHub.

7.12 Отправка истории

Создайте репозиторий через New repository в GitHub. Выберите имя и видимость Public либо Private. Для передачи готовой локальной истории оставьте исходный репозиторий пустым: без создания README, лицензии и .gitignore на сервере. Тогда первая отправка принесёт исходную историю проекта целиком. Создание репозитория.

В первой копии задайте origin, если он ещё не задан, и отправьте main:

git remote add origin git@github.com:OWNER/REPOSITORY.git
git push -u origin main

Push передаёт недостающие объекты и запрашивает обновление ветки на сервере. После успешной отправки серверная main указывает на M. -u сохраняет связь локальной main с origin/main как её upstream: эту связь Git использует при последующих операциях и сравнении веток. Право записи в выбранный репозиторий проверяется сервером при push. Руководство push.

7.13 Получение второй копии

Перейдите в родительский каталог latency-demo. Команда создаст новую соседнюю папку; имя latency-check должно быть свободно:

git clone git@github.com:OWNER/REPOSITORY.git latency-check

Clone создаёт локальный репозиторий, получает историю и разворачивает рабочие файлы выбранной начальной ветки. В обычной новой копии появятся main, локальное наблюдение origin/main и настройка remote origin. Перейдите в latency-check и сравните её с первой копией:

git rev-parse HEAD
git remote -v
git --no-pager log --graph --oneline --decorate --all
git status --short

HEAD должен иметь идентификатор отправленного M, файлы — его содержимое, статус — быть чистым. Для нового локального коммита проверьте имя и почту автора: локальная конфигурация первой папки через clone не переносится. Руководство clone.

7.14 Получение обновлений

Пусть во второй копии в README.md добавили строку о проверке данных, сохранили новый коммит N с родителем M и выполнили git push origin main. На сервере main уже указывает на N. В первой копии по-прежнему сохранено последнее известное ей значение M:

первая копия                 GitHub                 вторая копия
main ──> M                   main ──> N ──> M      main ──> N ──> M
origin/main ──> M

В первой копии выполните:

git fetch origin
git --no-pager log --graph --oneline --decorate --all

Fetch получает объекты и обновляет настроенные ссылки наблюдения за удалённым репозиторием. После обычного fetch origin/main указывает на N, собственная main остаётся на M, рабочие файлы сохраняют M. [1, сс. 89–99], [2]

первая копия после fetch
origin/main ──> N ──> M
                     ^
              main ──┘

Теперь main можно продвинуть к полученному потомку:

git merge --ff-only origin/main

main, индекс и рабочие файлы обновятся до N. Если обе стороны создали свои коммиты от M, линии расходятся; потребуется выбранный способ интеграции. Обычный push отвергает обновление серверной ветки, которое потеряло бы уже имеющуюся на ней линию. Получение её истории и слияние позволяют сохранить обе работы. Правила push.

Команда pull объединяет получение истории с последующей интеграцией; её способ зависит от параметров и настройки. Раздельные fetch и merge позволяют прочитать полученный граф перед изменением собственной ветки. Формы операций и разбор диагностик находятся в справочнике Git.
