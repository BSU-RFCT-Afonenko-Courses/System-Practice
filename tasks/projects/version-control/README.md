# Техническая поставка «Управления версиями»

Предметный договор задаёт [каноническое условие](../../labs/version-control.qmd).
Действуют три самостоятельных проекта с ручным оцениванием:

- `local-history` — собственная история слияния; сдача содержит bundle,
  рабочие файлы и пояснение по условию.
- `github-ssh` — реальный обмен через GitHub по SSH; самостоятельный вход
  содержит каталог оборудования с двумя линейными коммитами.
- `restore-selected-state` — наблюдение индекса и рабочего файла;
  native Workspace сохраняет работу штатной отправкой, локальный маршрут
  использует объявленный в условии архив с историей.

Состав каждого комплекта объявлен в его `_metadata.yml`, локальные
инструкции — в `student/README.md`. Наблюдения команд и объяснения принимаются
по соответствующему условию; локальные исходники и тесты не подтверждают
реальный GitHub/SSH, Windows или эксплуатацию Workspace.

`seed.json` содержит обычные файлы демонстрационного и стартового ZIP.
`build_git_materials.py` создаёт demo с корнем `latency-demo`, starter с
`versioning/project` и перечень исходных файлов `initial-state.json`.
В этих двух ZIP нет готовой `.git` и истории решения. Нужные локальные
изменения сохраняют перед генерацией.

Из корня репозитория:

```sh
python3 tools/build_git_materials.py
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Два `seed_recipe.py` создают только объявленное исходное состояние своего
проекта в пустой подготовленной области. Общие Git helpers также использует
поставка добровольного проекта сопровождения. Тесты материалов проверяют
исходные байты; тесты сопровождения — настоящие локальные fetch, конфликт
и применение patch. Общие ZIP/tar.gz safeguards проверяются непосредственно
на читателях архивов без извлечения и исполнения присланного кода.
