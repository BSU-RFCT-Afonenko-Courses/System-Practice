4  Управление версиями

Создайте историю небольшого проекта измерений, подготовьте коммиты с согласованным содержимым, выполните слияние расходящихся веток с разрешением конфликта. Разместите историю в собственном репозитории GitHub по SSH и получите её во второй локальной копии.

Работа выполняется в одном маршруте: PowerShell 7/Windows либо fish/Linux. Нужны Git, текстовый редактор, доступ к GitHub и выбранный SSH-клиент с настроенным ключом. Полные опыты доступны во введении; механизмы — в теории состояния репозитория, ветвления и обмена. Формы команд и упаковка находятся в справочнике.

4.1 Исходный проект

Распакуйте стартовый архив в новую папку. Он содержит:

versioning/
└── project/
    ├── README.md
    ├── criteria.txt
    └── measurements.tsv

В исходной папке отсутствует .git; историю создаёте вы. Три файла образуют текстово-табличный проект. Программу обработки писать не требуется.

Файл Исходное свойство
criteria.txt Единственная строка latency_limit = 25 ms
measurements.tsv Столбцы sensor, latency_ms; записи north, 18 и south, 28; разделитель TAB
README.md Назначение проекта; исходные измерения выражены в миллисекундах; в отчёт включаются значения, не превышающие порог из criteria.txt

Файлы имеют кодировку UTF-8. Окончания строк LF и CRLF допустимы. Состав и значения measurements.tsv сохраняются на протяжении работы. Имена, почта, даты, идентификаторы и сообщения собственных коммитов выбираются самостоятельно; сообщения должны описывать изменения.

4.2 Локальная история

Инициализируйте репозиторий в project с основной веткой main. Задайте сведения об авторе и сохраните начальный снимок трёх файлов. Для объяснения назовём этот коммит A.

От исходного состояния развиваются два самостоятельных изменения:

  1. В основной линии увеличьте порог до 30 ms. Новое состояние обозначим B.
  2. В отдельной ветке выразите исходный порог 25 ms в секундах: latency_limit = 0.025 s. Дополните README.md пояснением, что порог записывается в секундах. Состояние этой линии обозначим F.

Выберите имя рабочей ветки и порядок действий. В момент соединения истории B и F должны расходиться: обе продолжают A, ни одна из них не включает другую. Чтение их criteria.txt должно показывать два указанных изменения.

Перед одним из коммитов сохраните короткое наблюдение подготовки: состояние файла в рабочем дереве, содержимое подготовленного изменения и выбранный снимок. При разборе объясните по status и соответствующим diff, какое содержимое попадёт в обычный commit. Полный журнал команд для этого не требуется.

4.3 Слияние

Объедините расходящиеся линии операцией merge с коммитом слияния. Разрешите возникший конфликт criteria.txt так, чтобы итог одновременно сохранил увеличение порога до 30 ms и запись в секундах. Коммит слияния обозначим D.

Итоговые свойства основной ветки:

  • criteria.txt содержит latency_limit = 0.030 s; равнозначная запись 0.03 s допускается;
  • README.md сохраняет назначение исходных измерений и поясняет единицу записи порога;
  • measurements.tsv сохраняет исходные данные и единицу ms;
  • D имеет двух родителей, которые сохраняют обе расходившиеся линии; исходные A, B и F достижимы из итоговой main;
  • рабочая ветка сохранена на F либо на включённом в main продолжении F;
  • HEAD выбирает main; индекс и рабочее дерево совпадают с её снимком; маркеров конфликта и незавершённого слияния нет.

Проверьте величину порога через соотношение 1000 ms = 1 s. В пояснении покажите, какие два требования выполнены итоговой строкой. История слияния и корректное содержимое проверяются отдельно.

A, B, F, D — обозначения для объяснения; создавать одноимённые теги не требуется. Дополнительные содержательные коммиты допустимы при сохранении указанных состояний, расхождения и обеих линий родителей. Линейная история без требуемого двухродительского коммита не выполняет условие этой работы.

4.4 Размещение в GitHub

Используйте существующий личный аккаунт либо зарегистрируйте новый по официальной инструкции. Подтвердите почту, настройте защиту входа и сохраните способы восстановления в личном хранилище. Сведения автора коммитов выберите с учётом видимости почты в истории.

Настройте SSH-доступ. Можно использовать существующую пригодную пару ключей или создать новую под свободным именем. Существующие ключи сохраняются. На Windows Git и проверочная команда должны использовать согласованный системный Windows OpenSSH со службой ssh-agent; маршрут приведён в подготовке.

При первом подключении сверяйте ключ сервера с официальными отпечатками GitHub. Проверка ssh -T git@github.com должна распознать ожидаемый аккаунт. Объясните её сообщение и штатный код завершения 1. Закрытый ключ, парольная фраза, токены и коды восстановления в проект и сдаваемые материалы не включаются.

Создайте пустой учебный репозиторий, выберите видимость Public либо Private, настройте remote и отправьте основную ветку по SSH. Проверьте на GitHub наличие отправленного коммита и файлов.

Получите вторую обычную локальную копию через SSH clone с GitHub в versioning/verification. Она должна иметь собственный каталог .git, чистое рабочее состояние и ту же основную вершину, которую вы отправили. Из её main должны быть доступны исходные состояния и коммит слияния. Сопоставьте идентификаторы и содержимое файлов обеих копий.

4.5 Пояснение

Создайте versioning/explanation.md рядом с двумя репозиториями. Достаточно кратко записать:

  • ОС, оболочку, версию Git и выбранный SSH-клиент;
  • собственные идентификаторы A, B, F, D, имя рабочей ветки и родителей D;
  • наблюдение подготовки одного коммита и смысл выбранного снимка;
  • исходные стороны конфликта, итоговую величину и основание перевода единиц;
  • URL GitHub, видимость, распознанный SSH-аккаунт, результат отправки;
  • расположение второй копии, её origin, совпадающий идентификатор main и результат сравнения файлов.

На разборе покажите чтение нужного файла из истории, граф родителей, подготовку снимка и признаки внешнего обмена. Для SSH и GitHub подходят короткий сохранённый вывод существенных операций либо демонстрация с преподавателем. Секретные данные при демонстрации не открываются. Адрес remote и одинаковые файлы дополняются свидетельством реальных SSH push и clone: локальное копирование папки также могло бы дать совпадающее содержимое.

4.6 Сдача

Предъявите URL и архив каталога versioning, содержащий project, verification и explanation.md. Сохраняются оба .git с историей, ссылками, индексом и конфигурацией, а также рабочие файлы. Архив создаётся снаружи versioning. Принимаются ZIP и tar.gz. Способы упаковки включают скрытые каталоги и проверку восстановленной истории.

Перед сдачей извлеките архив в отдельную проверочную папку. В обеих извлечённых копиях должны читаться .git/HEAD, исходная история, итоговая вершина и чистое рабочее состояние. Извлечённые файлы совпадают с отправленным снимком. Такой контроль обнаруживает потерю .git при упаковке.

Для public преподаватель может открыть репозиторий непосредственно. Для private предоставьте преподавателю доступ к учебному репозиторию либо согласуйте показ его истории и внешнего обмена вместе с локальным архивом. Видимость менять ради сдачи не требуется. Архив позволяет проверить локальные файлы и отношения истории в обоих случаях; реальные действия GitHub/SSH принимаются по внешнему наблюдению.
